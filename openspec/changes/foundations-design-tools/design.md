# Design

## Context

The current backend integrates `foundations_shallow_loads`: a fifteen-quantity request, strict prepared source binding, shared R calculation, signed transfer, full-contact stop and four bearing checks. Its frontend feature is not integrated and still owns unfinished acceptance/review tasks. Existing dirty work in that feature and the current develop documentation checkout is unrelated to authoring this proposal and is preserved.

Akim confirmed preserving the averaged-weight mode, clarifying load meanings and adding a later explicit-weight alternative, then requested load schematics, pressure envelopes and footing sizing (working conversation, 2026-11-22). The public-source audit is evidence of differences, not admission of examples or approval of competitor constants. Current engineering input, source and reference records are in the pressure change and its paired readiness file. This design is a reviewable proposal; the decisions identified below remain unapproved.

## Goals / Non-goals

Deliver explicit load assembly, visual evidence and bounded size comparison without altering historical run identity or the generic executor. Keep modular-monolith services, repository persistence and typed immutable results. No queue, distributed service, new normative ingestion, deployment, automatic concrete geometry, partial contact, settlement or structural reinforcement design is introduced.

## Decisions

### 1. Preserve the existing public type

Do not turn the fifteen-input quantity map into a heterogeneous object or change what old fields mean. The proposed new registered type is `foundations_shallow_weights`, with nineteen scalar quantity inputs: the existing fifteen loads inputs minus the averaged-only weight thickness `d`, plus `G_fund`, `G_soil`, `G_other`, `Mx_add_base` and `My_add_base`. The existing fifteen-input averaged type is unchanged. The new type retains `h` as transfer arm and independent `d_1`/`d_b` for R; an unused averaged-weight thickness is not required or fabricated for diagrams. The proposed first new-type contract accepts structural loads at the upper cut only; its registered type and methodology identify the mode and load level without encoding strings as QuantityValue or adding scalar enum values to the old map. The scalar field contract and upper-cut/already-base moment semantics are those presented in the three references reviewed by Akim and admitted on 2026-11-22. Weights are nonnegative downward contributions; cut and added moments/shears are signed. No selectable base-level structural-load variant is introduced. Existing metadata can express scalar quantity inputs, units, labels and hints; a contribution list would require a broader API/form contract not assumed here.

`foundations_shallow_loads` remains the averaged mode with its original normalization, input hash, output order, source digest and version. Clarifying labels must not reinterpret historic requests or recalculate stored results. The new type receives distinct module/methodology identity and parameter-source allowlisting; catalog mode must remain fail-closed until a reviewed binding exists.

### 2. Assemble explicit resultants once

The approved explicit vertical assembly is N_base=N_II+G_fund+G_soil+G_other, p=N_base/A, with no gamma_mt*d*A term. Units are kN, m2 and kPa after the existing unit boundary. Each declared weight is supplied for that fixed geometry; no material density or volume is invented. Signed additional base moments capture asymmetric weights under the agreed x=b/y=l pressure-variation convention. No automatic reverse load-factor conversion is performed.

The proposed first contract fixes structural moments at the cut and `Mx_add_base`/`My_add_base` at the base: structural moments receive M+Q*h once, then the named base additions are added once. A separately selected base-level structural-load variant would need an additive discriminated request contract or distinct registered identity; it is not silently represented by numeric enums or an unlabelled h=0 convention. The first release is upper-cut-only with nonnegative downward weights; Akim reviewed that assembly in all three references and confirmed final admission. Existing R, unrounded pressure comparisons, minimum-corner contact refusal, edge/corner limits and deciding-check rules are reused without copying competitor coefficients.

Source ownership: existing averaged pressure components use prepared SP 22.13330.2016, edition 2016 with amendments 1-5, clauses 5.6.28-5.6.29; limits use clause 5.6.26. New vertical and signed moment assembly is the EngineerRule recorded by Akim's reference and contract approvals on 2026-11-22. No NormRef status is promoted.

After unit normalization, require N_base=N+G_fund+G_soil+G_other > 0. Akim explicitly confirmed this engineering applicability rule on 2026-11-22. A nonpositive resultant is invalid_input before calculation, regardless of zero or nonzero moments; the error names the contributing scalar inputs. Do not divide by zero, return a zero-pressure success or reinterpret this as partial contact. The existing nonnegative component and finite-quantity validation remains. This new-type rule does not change the historical averaged type.

### 3. Store diagram context, then render it

Use a domain presentation sidecar, not new mandatory fields on ResultEnvelope or branches in the generic module outcome. A `foundation_result_context` row keyed by `result_id` stores `schema_version="foundation-result-context-v1"`, calculation type, methodology identity, original quantity inputs and typed visualization data. The sidecar is immutable and shares the ordinary result transaction. Emit it for new explicit-weight results and for new averaged-mode results evaluated by this domain workflow. Old calculation envelopes and their identity remain byte-compatible, and rows without sidecars remain valid.

`GET /foundation-calculations/{result_id}/context` returns the stored sidecar with HTTP 200 or structured 404 `foundation_context_unavailable` when a stored legacy result lacks it; it never calculates or reconstructs missing context on read. The absent-context UI retains the existing trace/table and says a diagram is unavailable, rather than guessing inputs from the envelope. General old `GET /calculations/{result_id}` remains unchanged. `POST /calculations` for the new registered explicit-weight type keeps the existing quantity-map body and response; the frontend follows the ordinary returned result ID to request optional domain context. Adding a sidecar for future ordinary averaged results is an explicitly tested service-side addition with no change to their request or envelope. Historical diagram retrofitting is outside this release.

Visualization data identify the footing rectangle, `x=b` and `y=l`, load level and weight mode, signed applied loads, transfer arm, added weight contributions, and base resultants. Every physical value references its stored input key or typed trace step. The backend stores four ordered corner coordinates and signed pressures plus minimum/maximum selection. It also stores the finite pressure samples needed by the chosen drawing; the frontend may scale/project coordinates and place labels but does not derive physical pressures, compare values, select a corner or decide a check. The nineteen-input explicit type does not supply a separate concrete block height; its schematic therefore shows the load plane and the declared transfer arm, not invented foundation geometry.

The frontend renders accessible SVG and a matching text/table alternative. Trace details remain initially expanded under the current pressure amendment. A derived refusal may carry completed signed diagnostic pressure evidence labelled outside full-contact applicability; it must not show a redistributed active-area surface or final bearing outputs. A pre-calculation bound refusal contains no pressure surface. DOCX consumes the same stored sidecar and trace; absence on a historical report preserves existing rendering. Complete vertical/moment sums include every stored contribution.

### 4. Candidate selection is a separate typed workflow

Akim confirmed the first-release scope on 2026-11-22: an engineer-supplied finite explicit list of `(b,l)` pairs, averaged weights only, with minimum area among passing candidates. This establishes neither a default series nor global optimization. Akim confirmed first-submitted order for equal minimum area and a 256-candidate technical cap on 2026-11-22. Engineering input signs and the upper-cut/already-base split follow the admitted reference contract. Explicit-weight search is rejected because one geometry's component weights must not be reused at other dimensions.

Use these additive routes with strict schemas rejecting unknown fields:

- `POST /foundation-selections`: synchronous evaluation and immutable storage, HTTP 201 with `Location: /foundation-selections/{selection_id}` for every stored terminal outcome.
- `GET /foundation-selections/{selection_id}`: HTTP 200 containing that terminal stored outcome without reevaluation.
- `POST /foundation-selections/{selection_id}/report`: the existing ReportRequest structure and DOCX media type, built only from the stored search record and any linked selected result. It supports no-solution and incomplete evidence without a success conclusion.

The request has `schema_version="foundation-selection-request-v1"`, `calculation_type="foundations_shallow_loads"`, `policy_version="foundation-min-area-v1"`, a `common_inputs` quantity map containing exactly the registered inputs except `b` and `l`, and `candidates`, a non-empty ordered array of strict objects `{b: QuantityValue, l: QuantityValue}`. The confirmed policy selects minimum area among passing candidates, breaking equal-area ties by the first original input index. No strings, mode enums or candidate lists are encoded as QuantityValue. The technical cap is 256 submitted candidates; the existing global 1 MiB body limit remains unchanged. The count limit bounds sequential work and retained traces without inventing dimensional/application limits. Validate all candidates and units before evaluating any; reject malformed dimensions, reversed orientation, missing/common `b` or `l`, undeclared quantities and wrong calculation type with named-field 422. Convert using the existing boundary and retain original units/order. Do not swap axes or silently deduplicate identical entries; their original indices remain distinct evidence.

A domain service constructs one ordinary candidate request per original index. For each it resolves R and all source-dependent parameters at that candidate's geometry and invokes the existing pure registered calculation. It must not reuse one candidate's R, assume monotonic behavior or prune candidates. The typed immutable response uses `schema_version="foundation-selection-result-v1"`, a server `selection_id`, stable search input hash, policy/methodology identity, original request, and candidate outcomes in request order. Each evaluated outcome retains the complete calculation/refusal evidence, original inputs, source description/digest and module input hash; skipped indices retain an explicit reason. Candidate results are not ordinary persisted results merely because they were evaluated.

Terminal `status` is exactly `selected`, `no_acceptable_candidate` or `incomplete`. Only `selected` contains `selected_candidate_index` and `selected_result_id`; both are null otherwise. An all-evaluated set without a passing candidate is `no_acceptable_candidate`. Source-resolution failure, unexpected candidate calculation error, evaluation deadline or cancellation yields `incomplete` with a typed reason and the attempted/unattempted indices. These are never treated as bearing failures that permit choosing from an incomplete set. Validation and database failures remain the existing structured 422/413/503 error responses and are not represented as a stored successful selection. Full-contact refusals and legitimate check failures remain inspectable ordinary candidate outcomes.

Persist a single `FoundationSelectionRow` containing immutable request/outcome JSON, schema/policy versions, identity and optional selected-result foreign key. For a complete selected outcome, create the ordinary chosen CalculationResultRow, its visualization sidecar and the selection row in one application-database transaction. Generate storage IDs outside the pure engine, flush to validate, and commit once through a service-owned unit of work. Reuse the evaluated winning envelope; do not call submit() in a way that recalculates it or commits independently. Any write failure rolls back all three records. Other candidate traces stay in the selection JSON, so they do not create orphan ordinary results. No-solution/incomplete outcomes create only their selection record. Retrieval/reporting reads those immutable records. The schema migration is additive, with foreign keys and reversible downgrade on a task-specific test database; planning does not execute it.

Search evaluation is request-scoped sequential work within the modular monolith, not a queue, worker process or optimizer service. The service uses a 10-second cooperative evaluation budget measured with monotonic time outside the pure engine. It checks before and after each candidate and before final selection. A single source/calculation operation is not forcibly killed; therefore this is an evaluation budget, not a promised hard 10-second HTTP deadline. A budget breach prevents selection even if some previous candidates passed. Database commit/report time is measured separately. Candidate work may use the framework's normal thread execution boundary so an async route can observe disconnects; no unbounded per-candidate concurrency or detached background task is introduced.

Client cancellation aborts its request and retains the draft; the service observes disconnect/cancellation at the next safe candidate/commit boundary and creates no winner after acknowledging it. If storage is still available, a terminal `incomplete/cancelled` audit record may be committed without a selected result; a disconnected client cannot be promised receipt of its ID. Cancellation after the atomic commit cannot delete or rewrite an immutable completed result. The UI must state this race and must not claim a completed design was undone. This release does not add cancel/resume endpoints or resumable jobs. Unit/integration tests must cover cancellation before work, between candidates and before/after commit.

Successful complete searches are reproducible for identical candidate order, source identities and approved policy, apart from permitted storage identifiers. Timing/cancellation are operational observations, not deterministic engine inputs: incomplete stop points are stored as observed and are not promised to repeat. The stable input identity excludes wall-clock measurements and generated IDs; it includes normalized common/candidate quantities in original order, policy/methodology versions and the ordered resolved candidate data identities. Incomplete records explicitly mark identities of unevaluated candidates as unavailable and cannot share a certified-selection identity.

### 5. Component and feature boundaries

`backend/app/engine/` owns pure new-type assembly and candidate calculation; `services/` orchestrates source resolution, bounded iteration and persistence, and repositories own search/result rows. Existing imports/layers remain enforced. The pure module `calculate` boundary remains the future C/C++ replacement interface; orchestration, HTTP, database, SVG and DOCX remain outside. Do not edit the shared generic executor to connect this feature; a required executor modification exposes a separate contract gap.

Backend feature: `feature/foundations-design-tools/backend`, from develop after the reviewed pressure backend dependency. Frontend feature: `feature/foundations-design-tools/frontend`, from develop after the preceding loads frontend has its own tester GO, review and authorized integration. The new backend integrates before the new frontend. There is no automatic merge, cherry-pick or commitment of dirty prerequisite work. New planning documents stay on develop. Explicit Git consent remains separate.

### 6. Verification and technical limits

Before implementation, approve named independent reference derivations and per-output tolerance provenance for the new type under the applicable origin policy; do not extend the existing manual exception automatically. At least three complete examples are required for a new registered calculation type. Search needs exhaustive small-list controls, tie and no-solution examples, source-resolution failure and interrupted-search behavior, plus repeated-run identity.

The chosen transport controls are 1-256 candidates, the existing 1 MiB body cap and a 10-second cooperative evaluation budget, with the terminal/error/cancellation semantics in decision 4. These are technical safety controls, not normative applicability bounds or measured performance promises. Before DOR, review the concrete API/unit-of-work design and its tests; a benchmark may require revising the cap before enabling the route. Existing API/report latency targets remain; measure search separately with candidate counts and named environment instead of inventing a typical-design benchmark.

Backend ruff, mypy, import boundaries and tests; frontend drift, ESLint, TypeScript, Vitest; branch coverage at least 95%; Playwright; UI/UX; source traceability and current spec review are acceptance gates. Historical pilot and averaged reference fixtures remain frozen. Real DB/catalog integration checks and all skips are recorded separately. The unresolved full branded browser-matrix gate of the prior frontend is not waived here.

## Risks / Trade-offs

- A new registered type adds metadata/source binding work but keeps old request meaning and identity stable.
- Reusing one externally computed G across candidates gives misleading size selection; the initial search restriction prevents that shortcut.
- Matching a competitor's pass verdict may hide different load levels, weights, signs or corner criteria. Independent arithmetic and sources control acceptance.
- Diagram readability can imply a solved partial-contact problem. Diagnostic labels and absent final outputs must remain explicit.
- Candidate count and full traces increase storage and latency. The initial technical cap of 256 and explicit result schema need measured validation before enabling search; do not advertise the cap as an engineering application limit.

## Migration Plan

Resolve engineering questions and prerequisite gates, obtain current review and DOR, then implement backend and frontend on their own branches. Add new result context optionally and search persistence additively. Deploying or running migration requires its own authorized task. Rollback disables the new type/search controls while retaining all immutable records and historical rendering. Archive only after accepted reviewed integration of both features and final validation.
