# NLP-извлечение из нормативов: решение и план интеграции

Резюме исследования `ml/research/nb01..nb04`. Цель — определить, что из ML-подхода
внедряем в `normatives_pipeline` сейчас, а что откладываем, и на каких числах это решение
основано. Пилотный документ — СП 22.13330.2016 (text-based PDF, есть текстовый слой).

## 1. Резюме решения

| Задача | Модель | Вердикт | Почему |
|---|---|---|---|
| Layout (блоки таблиц/формул/подписей) | DocLayout-YOLO | **Внедрять** | работает по растру, не зависит от языка и regex-подписей |
| Структура таблицы (строки/колонки) | pdfplumber `find_tables` (существующий) | **Оставить основным** | на text-based PDF извлекает таблицу 4.1 корректно (5 строк, header, перенос номера) |
| Структура таблицы (строки/колонки) | TableTransformer | **Только для сканов/сложных** | пока хуже pdfplumber: 3 строки вместо 5, header не отделён |
| End-to-end страница → Markdown | Nougat-base | **Не внедрять** | на русском даёт пустоту/мусор, без fine-tune бесполезен |
| Распознавание формул → LaTeX | pix2text (LatexOCR) | **Внедрять** (уже есть) | уверенно читает формулы, но нужна усиленная нормализация |
| Распознавание формул → LaTeX | texify | **Не внедрять** | несовместим со стеком (transformers 4.57.6 + pdfplumber) |
| NER обозначений/единиц | rubert-tiny2 (fine-tune) | **Отложить** | нет NER-головы и размеченного корпуса, вне MVP |
| Нормализация обозначений | rubert-tiny2 embeddings | **Опционально** | группирует варианты написания (`γII`≈`гамма_II`=0.85) |

**Главный вывод:** end-to-end «одна модель вместо пайплайна» (Nougat) для русских
нормативов не работает без дорогого fine-tune. Побеждает **слоистый подход**: layout
(DocLayout-YOLO) → формулы (pix2text) → таблицы (TableTransformer) → содержимое
(pdfplumber / OCR для сканов). Каждая модель обучена на своей задаче и не завязана на язык.

## 2.1 Проверка на СП 31.13330.2021 (второй документ)

Второй пилот — СП 31.13330.2021 «Водоснабжение. Наружные сети» (160 стр., text-based).
Проверка выявила главный нерешаемый нормализацией блокер: **кириллические индексы**.

| Задача | Метод | Результат |
|---|---|---|
| Формулы (детекция) | regex `extract_formulas` | 13 формул (номера 1–11, 13) |
| Формулы (детекция) | DocLayout-YOLO | **21** isolate_formula + 19 formula_caption (находит на стр. 88/142/155/156, где regex не справился) |
| Формулы (распознавание) | pix2text → latex2sympy2 | **4/21 (19%)** парсится |
| Формулы (после `correct_latex` v2) | pix2text → `canonical_latex` | **10/21 (48%)** парсится |
| Таблицы (содержимое) | pdfplumber `find_tables` | 84 таблицы, из них **45 без номера (53%)** |
| Таблицы (layout) | DocLayout-YOLO | 69 `table` + 53 `table_caption` |

**Главная причина провала формул** — pix2text не обучен на кириллице: русские индексы
распознаются как побуквенная латиница с пробелами и путаницей букв/цифр:

- `F_{Б.о} = q β_{0,6} / 3,6 v_p N_p` → `F_{\tt B.o}=q \beta_{\tt 06} / 3 {\tt,} 6 v_{p} N_{p}`
- `h_{зар} = h_{расч} + 0,3` → `h_{\mathrm{\tiny{3 a r r o m}}} \!=h_{\mathrm{\tiny{r u y 6.}}}...`
- `λ_с = λ_о (e^{αT_{пр}} - 1)/(αT_{пр})` → `\lambda_{c}=\lambda_{o}... \enspace`

Парсятся только формулы без кириллицы в критичных местах (`N_{TM} = sqrt(F_{TM}/2)`,
`i = K q^n / d^p`).

**Вывод:** `correct_latex` решает системные артефакты (`\not`, `{\tt}`/`\tt`, `\enspace`,
десятичная запятая, `\[`/`\]`, пустые `{}`, стили `\boldsymbol`/`\mathit`/`\tiny`…).
После усиления (этап 1 выполнен, `ml/tests/test_detect.py`) парсинг вырос с 19% до **48%**
(10/21): парсятся все чисто-латинские формулы и формулы с транслит-индексами
(`PN ≥ (P_{pa6}+P_τ)/1.4`, `λ_с = λ_о(e^{αT_np}-1)/(αT_np)`, `F_{Б.о} = q β_{0,6}/3.6 v_p N_p`).

Оставшиеся 11/21 не парсятся в основном из-за **кириллических индексов**, которые pix2text
распознаёт побуквенной латиницей с путаницей букв/цифр (`h_{зар}`→`h_{3arrom}`,
`h_{расч}`→`h_{ruy6.}`), и одного структурного случая (`\Sigma` вместо `\sum`).

## 3. Что внедряем и как (по приоритету)

### P0 — усилить нормализацию формул

Проблема из nb03 + СП 31: pix2text выдаёт визуально верный LaTeX, но `latex2sympy2` парсит
14–19%. Текущий `formulas/detect.py::correct_latex` убирал лишь `~`, `\,`, `\;`, `\qquad`, `\quad`.

**Этап 1 (выполнен):** расширен `correct_latex` (`ml/src/normatives_pipeline/formulas/detect.py`):
`\not`, `{\tt}`/`\tt`, `\enspace`/`\qquad`/`\quad`, `\boldsymbol`/`\mathit`/`\mathsf`/`\textsf`/
`\mathtt`/`\tiny`/`\scriptsize`/`\scriptstyle`, десятичная запятая `0 , 7` → `0.7`, `\[`/`\]` → `[`/`]`,
пустые `{}`. Тесты `ml/tests/test_detect.py`. **Результат на СП 31: парсинг 19% → 48% (10/21).**

**Этап 2 (кириллические индексы) — варианты, от дешёвого к дорогому:**

| # | Подход | Плюсы | Минусы | Вердикт |
|---|---|---|---|---|
| A | Словарь обозначений `extract_formula_notation` + транслит-нормализация + fuzzy-match (Левенштейн) | быстро, инфраструктура готова | сопоставление ненадёжно из-за путаницы б/6, з/3, д/g; покрывает только формулы с «где» | **начать с этого** |
| B | Гибрид: pix2text даёт структуру (дроби/индексы), кириллический OCR (surya / PaddleOCR ru) даёт правильные русские индексы по позиции | надёжно, не зависит от словаря | сложное выравнивание bbox↔индексы, новый OCR в стеке | **после A** |
| C | Fine-tune LaTeX-OCR на синтетическом русском датасете (рендер `h_{\text{зар}}` → изображение → пары) | правильное долгосрочное решение | дорого, отдельный проект | **стратегически** |

Дополнительно для A: текстовый слой PDF (`pdftotext`) сохраняет кириллицу обозначений в юникоде
уже корректно — его использовать как источник правды вместо побуквенного транслита pix2text.

**Критерий приёмки (этап 1):** ≥ 90% формул **без кириллических индексов** парсятся. 
**Критерий приёмки (этап 2):** ≥ 90% всех распознанных формул парсятся после восстановления
индексов. Владелец зоны — **Akim** (calculation engine / formula pipeline).

### P1 — layout DocLayout-YOLO в пайплайн (замена regex-детекции блоков)

Проблема из nb01: regex ищет `Таблица N` / `изолированные формулы` по подписи — не
обобщается. DocLayout-YOLO даёт блоки `table`, `table_caption`, `isolate_formula` по растру.

**Действие:** добавить в пайплайн этап layout-детекции, который по bbox блоков сегментирует
страницу; regex остаётся как fallback для text-based PDF. `table_caption` даёт номер таблицы
независимо от формата подписи.

**Критерий приёмки:** на СП 22.13330.2016 таблицы/формулы обнаруживаются по layout не хуже
regex (совпадение по числу и страницам), плюс работает на сканах без текстового слоя.
Владелец — **Egor** (data-zone, `normatives_pipeline`).

### P2 — TableTransformer: только для сканов и сложных таблиц

Важная поправка по факту: существующий `extract_tables` (pdfplumber `find_tables`) уже
извлекает таблицу 4.1 корректно — 5 строк (header + I/II/III), с переносом номера таблицы
между страницами. Мой ML-прототип (TableTransformer) пока **хуже**: 3 строки вместо 5 —
потерял строки II/III из-за обрезки bbox DocLayout-YOLO, header от данных не отделён.

**Вывод:** для text-based PDF pdfplumber остаётся основным. TableTransformer нужен только
когда текстового слоя нет (сканы) или таблица имеет сложный spanning, который `find_tables`
не разбирает. Перед внедрением решить: (1) корректный bbox (не обрезать таблицу), (2) header
vs data, (3) spanning cell, (4) склейка таблиц, продолжение которых DocLayout-YOLO видит как
отдельный `table`-блок на следующей странице.

**Критерий приёмки:** на размеченном вручную наборе (смесь text-based и сканов) точность
структуры TableTransformer ≥ точности pdfplumber на text-based; на сканах — работает там, где
pdfplumber не может. Владелец — **Egor** (data-zone).

### P3 — отложить (не в MVP)

- **Nougat fine-tune** на русских нормативных PDF — дорого, нет размеченного корпуса.
- **NER (token classification)** обозначений/единиц — нужен fine-tune на NEREL/собственной
  разметке; пока закрывается regex `symbols.py` + `extract_formula_notation`.
- **texify** — вернуться только при переходе на совместимый стек (нужен transformers<4.40
  или апгрейд texify), в изолированном окружении.
- **OCR для сканов** (Tesseract ru / PaddleOCR) — отдельная задача, когда появятся
  сканированные нормативы.

## 4. Что нужно, чтобы действовать дальше честно

Сейчас все метрики — на одном пилотном СП 22.13330.2016 (text-based). Для принятия решений
по P1/P2 нужен **validation-датасет**:

- 10–20 таблиц с эталонной разметкой (строки/колонки/header/spanning, переносы по страницам).
- 30–50 формул с эталонным LaTeX (в т.ч. греческие буквы, индексы, дроби, суммы).
- 2–3 разных документа (другой СП/ГОСТ) для проверки обобщаемости.

Это отдельная задача (разметка вручную или полуавтоматически), после которой P1/P2 можно
оценивать по DOD (coverage ≥95%, тесты, GO/NO-GO).
