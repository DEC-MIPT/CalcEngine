## 3. Предлагаемые OpenSpec change

По одному change на пакет. На этом шаге ничего не создаётся. Ни одно требование ниже не
фиксирует нормативное значение: допуски, границы и правила округления — это поля данных,
которые инженер заполняет по первоисточнику.

**Общий интерфейс** между WP2 и WP3, согласовать до написания любого из них:
`NormRef {document, edition, clause, status, provenance}`. `edition` и `clause` могут
быть `unverified`; ни одно поле не может быть пустым (null).

### 3.1 `retarget-mvp-domain` (WP1)

- **Цель:** направить все спеки и AI-контекст на подтверждённый домен MVP и письменно
  зафиксировать объём.
- **Capabilities:**
  - MODIFIED: `product-vision`, `calculation-engine` (сценарий), `normatives-catalog`
    (назначение, сценарий), `transparent-output` (пример), `web-platform`,
    `user-accounts`.
  - ADDED: одна capability для первого домена (`foundations-shallow` или
    `water-supply-internal`) — только требования об объёме.
  - Вне capabilities: контекст в `openspec/config.yaml`.
- **Ключевые требования:**
  1. Объём MVP называет оба домена и их порядок. *WHEN MVP сдан THEN типы расчётов
     первого домена работают от начала до конца; второй домен следует к названной вехе.*
  2. Явный список out-of-scope для первого домена. *WHEN пользователь запрашивает случай
     из списка THEN система отказывает и называет ограничение.*
  3. Non-goals до защиты (интеграция оплаты, NLP в продукте, PDF, журнал аудита для
     нескольких организаций и др.; список утверждает PM). *WHEN предложение затрагивает
     non-goal THEN сначала изменяется product-vision.*
  4. Ссылка на норму в спеке либо сверена с текстом источника, либо помечена
     `source: unverified`. *WHEN спека приводит пример ссылки THEN используется
     синтетическая заглушка.*
  5. У каждого требования один владелец: авторизация живёт в `user-accounts`, лимит B2C —
     ровно в одной спеке. *WHEN две спеки формулируют одно правило THEN одна из них
     только ссылается на другую.*
- **Готово, когда:**
  - `grep -ri "beam\|16\.13330" openspec/ --exclude-dir=archive` даёт 0 совпадений.
  - `openspec validate --all --strict` проходит.
  - `spec-reviewer` не находит блокеров.
  - PM утвердил список non-goals и лимит B2C.
- **Владелец:** DE (ведёт), Аким (соавтор), PM (утверждает объём).

### 3.2 `calculation-core-contract` (WP2)

- **Цель:** не зависящий от домена контракт движка, который потребляют UI и отчёт.
  Здесь «белый ящик» становится проверяемым.
- **Capabilities:** MODIFIED `calculation-engine`, `transparent-output`,
  `report-generator`.
- **Ключевые требования:**
  1. **Чистый расчёт.** Расчётная функция принимает типизированные входные данные и
     готовые параметры и возвращает конверт результата, без ввода-вывода. *WHEN
     функция запускается с подменёнными файловой системой и сетью, которые падают при
     обращении, THEN она завершается, и одинаковые входные данные дают одинаковый конверт.*
  2. **Типизированный шаг трассы.** Каждый шаг содержит `{step_id, expression
     (renderable), substitutions with units, result with unit, norm_ref}`. *WHEN расчёт
     завершён THEN у каждого шага есть эти поля; шаг без проверенного `norm_ref`
     помечается и учитывается.*
  3. **Явные единицы.** Единицы есть везде, пересчёт — только на границе. Каждая
     выходная величина объявляет правило округления и его источник. *WHEN входная
     величина приходит не в базовой единице THEN она пересчитывается на границе, и
     трасса показывает базовую единицу.*
  4. **Проверка применимости с тремя исходами.**
     - *WHEN входные данные в пределах метода THEN расчёт выполняется.*
     - *WHEN входные данные вне пределов метода THEN расчёт отклоняется с указанием
       границы и её `norm_ref`.*
     - *WHEN входные данные в пределах метода, но вне проверенной области THEN расчёт
       выполняется, а предупреждение переносится в UI и отчёт.*
  5. **Конверт результата и ответственность.** Конверт содержит `result_id`, версию
     движка, хеш входных данных, использованные `norm_ref`, вердикт и предупреждения.
     Отчёт печатает всё это и утверждение, что за результат отвечает инженер. *WHEN
     отчёт сформирован THEN эти поля в нём есть.* Обязательность подписей оставлена на
     проверку по ГОСТ Р 21.101 (`unverified`).
- **Заметка к дизайну (C10):** схема ввода каждого типа расчёта — единственный источник
  валидации для API и формы; способ генерации решается в `design.md`.
- **Готово, когда:**
  - `NormRef` согласован с DE.
  - Валидация проходит, `spec-reviewer` не находит блокеров.
  - `norm-traceability-checker` подтверждает, что ни одно требование не фиксирует
    нормативное значение.
- **Владелец:** Аким; DE проверяет `NormRef`.

### 3.3 `norm-source-traceability` (WP3)

- **Цель:** каждое нормативное значение, которое использует расчёт, несёт источник и
  редакцию, а каждый сохранённый результат остаётся привязан к тому, что использовал.
- **Capabilities:**
  - MODIFIED: `normatives-catalog` (требование об актуальности становится моделью
    статусов).
  - ADDED: требования о происхождении данных и фиксации редакции.
  - Переносит половину `agent-docs/domain-constraints.md`, относящуюся к каталогу, в спеку.
- **Ключевые требования:**
  1. Каждая запись нормативного параметра, в `params/` или в БД, содержит `NormRef`.
     *WHEN у записи файла параметров нет источника THEN валидация схемы не проходит.*
  2. Статус документа — действует, заменён или отменён; менять его может только
     сопровождающий. *WHEN привязанная редакция становится заменённой THEN типы
     расчётов, которые её используют, показывают предупреждение.*
  3. Сохранённый результат навсегда привязан к `{document, edition, clause set}` через
     денормализованные колонки в `dec_app` (B3). Он никогда не пересчитывается молча.
     *WHEN редакция заменена THEN старые результаты сохраняют значения и показывают
     отметку.*
  4. **Происхождение.** Значение либо `human-verified`, либо `machine-extracted`;
     движок принимает только `human-verified`. *WHEN слой параметров загружает значение
     `machine-extracted` THEN он его отклоняет.*
  5. Система хранит только те виды нормативного содержимого, которые разрешает
     записанное правовое решение: ссылку, пересказ или полный текст (C5). *WHEN
     загрузчик принимает источник THEN он сохраняет только разрешённые поля.* Если у PM
     ещё нет ответа, это требование явно откладывается.
- **Готово, когда:**
  - Ответ по C5 записан, или требование 5 отложено.
  - `NormRef` согласован.
  - Валидация проходит, `norm-traceability-checker` проходит на этом change.
- **Владелец:** DE; Аким проверяет требования 1 и 3.

### 3.4 `calculation-verification` (WP4)

- **Цель:** гейт по правильности, а не только по покрытию.
- **Capabilities:**
  - ADDED: `calculation-verification`.
  - MODIFIED: `calculation-engine` (заменяет требование о точности) и
    `development-process` (правило GO для изменений в расчётах).
- **Ключевые требования:**
  1. Каждый тип расчёта поставляется минимум с N эталонными примерами (N согласуется;
     аудит предлагает 3). У каждого примера указано происхождение (ручной расчёт,
     учебник или приложение нормы) и допуск по каждой величине, который задаёт инженер.
     *WHEN запускается набор эталонов THEN каждая величина укладывается в допуск, иначе
     вердикт NO-GO.*
  2. «Точность 99,9%» заменяется требованием 1, а цель по задержке 30 с становится
     отдельным требованием. *WHEN заявляется точность THEN она выражена как отклонение от
     названных эталонов.*
  3. **Регрессионный корпус.** Зафиксированный набор `(inputs, edition) → outputs`
     перезапускается при каждом изменении. *WHEN результат отличается THEN сборка
     падает, если change не объявляет это отличие.*
  4. **Тесты инвариантов.** Для каждого типа расчёта перечислены инварианты, которые
     выполняются независимо от нормы (детерминизм, согласованность при смене единиц и
     другие, подтверждённые инженером), и на каждый есть property-тест. *WHEN входные
     данные генерируются случайно в допустимом диапазоне THEN каждый инвариант
     выполняется.*
  5. **Метрики на каждый прогон:** отклонение от эталонов, полнота трассируемости (доля
     шагов с проверенным `NormRef`) и доля воспроизводимых результатов. *WHEN tester
     выдаёт GO THEN три метрики приложены.*
- **Готово, когда:**
  - Первый домен выбран, и назван хотя бы один источник эталонных примеров.
  - Изменения в `tester` и `test-process` согласованы с DE, потому что это общие файлы.
- **Владелец:** Аким. Эталонные примеры нужны от инженера; кто это — нужны данные.

### 3.5 `backend-layered-architecture` (WP5): обновить существующий change, а не создавать новый

- **Цель:** согласовать активный change с WP1–WP3 и сделать так, чтобы он проходил DOR.
- **Capabilities:** `backend-architecture` (дельта).
- **Ключевые требования:**
  1. Доменные подпакеты в `engine/` и `parameters/`, по одному на инженерный домен;
     доменный модуль не может импортировать другой доменный модуль. *WHEN домен A
     импортирует домен B THEN проверка контракта импортов падает.*
  2. Направление зависимостей охватывает все слои (включая `schemas`, `core` и `db`) и
     проверяется автоматическим контрактом импортов. *WHEN модуль импортирует из более
     высокого слоя THEN проверка падает.*
  3. Движок получает параметры типизированными аргументами (задача 6.2
     переформулирована). *WHEN движок работает THEN он не вызывает загрузчик параметров.*
  4. Расчёт в MVP синхронный, `worker` удалён; альтернатива — описать контракт задания.
     *WHEN запрошен расчёт THEN HTTP-ответ содержит результат в пределах заявленной
     задержки.*
  5. Нефункциональные требования записаны, включая отдельные роли БД для каждой зоны.
     Обоснование разделения на две БД и фиксации редакции идёт в `design.md`.
- **Исправления артефактов:**
  - Добавить Non-goals в `proposal.md`.
  - Дать каждой задаче зональную подветку, добавить DOR и DOD.
  - Заменить задачи про балку 4.2, 5.2 и 6.2 на пилот первого домена.
- **Готово, когда:** `spec-reviewer` не находит блокеров (в прошлый раз нашёл 5), и
  валидация проходит.
- **Владелец:** Аким и DE, задачи разделены по зональным подветкам.

### 3.6 `bootstrap-dev-environment` (WP6)

- **Цель:** минимальный набор инструментов, с которым первый код сможет пройти DOD.
- **Capabilities:** MODIFIED `development-process` (называет инструменты).
- **Ключевые требования:**
  1. Одна команда для backend запускает линтер, проверку типов и тесты с покрытием
     ветвей. *WHEN она запускается на чистом checkout THEN завершается с кодом 0.*
     Проверщик типов (`mypy` или `ty`) выбирается здесь.
  2. Frontend: `eslint`, `tsc` и `vitest` запускаются так же.
  3. Контракт импортов из WP5 входит в проверку. *WHEN есть импорт вверх THEN проверка
     падает.*
  4. Pre-commit-хук ищет секреты, а `.env.example` перечисляет все переменные, которые
     читает конфиг. *WHEN в индекс попадает секрет THEN коммит блокируется.*
  5. Docker compose поднимает PostgreSQL (обе БД) и backend. *WHEN выполняется
     `docker compose up` THEN health-эндпоинт отвечает.*
- **Готово, когда:** выбран проверщик типов, решено, где будет CI (или пока только
  локально), и валидация проходит.
- **Владелец:** Аким (требования 1–4), Егор (требование 5 и CI).

### 3.7 `team-roles-update` (WP7)

- **Цель:** процесс соответствует команде из трёх человек и умеет закрывать change без
  кода.
- **Capabilities:** MODIFIED `development-process`; `AGENTS.md` и `config.yaml`
  обновляются после согласия команды.
- **Ключевые требования:**
  1. **Роль PM.** PM отвечает за объём, цены и правовые вопросы и не имеет зоны кода.
     *WHEN нужно решение по объёму, ценам или правовому вопросу THEN его владелец — PM.*
  2. **GO для change без кода.** GO требует, чтобы валидация прошла, `spec-reviewer` не
     нашёл блокеров, а второй разработчик подтвердил change. Tester записывает, что тесты
     неприменимы. *WHEN в change нет кода THEN действует этот путь.* Это разблокирует
     `record-installed-skills-akim`.
  3. **DOR включает `spec-reviewer`**, потому что валидация проверяет только структуру.
     *WHEN change объявляется готовым THEN есть отчёт `spec-reviewer` без блокеров.*
  4. **Общие решения отслеживаются git.** Спеки ссылаются только на отслеживаемые
     источники. *WHEN дизайн приводит обоснование THEN он ссылается на отслеживаемый
     файл, а не на паспорт.*
- **Готово, когда:** Егор согласен (это общие файлы), и валидация проходит.
- **Владелец:** вместе.
