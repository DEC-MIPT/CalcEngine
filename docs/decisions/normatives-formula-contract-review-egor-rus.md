## Две формы

Согласованный `NormRef`:

```
NormRef { document, edition, clause, status, provenance }
```

`norm_ref` в payload сейчас (`parser.toml`: `norm_ref_keys = ["designation", "clause", "formula"]`):

```json
{"designation": "СП 45.13330.2017", "clause": "13.8", "formula": "13.8#1"}
```

## Вопросы

### 1. Согласен с замечаниями 1–8?

**Ответ.** Согласен со всеми восемью. Мой payload расходится с уже согласованным `NormRef`. Исправляю: `norm_ref` несёт `document`, `edition`, `clause` (один локатор, каноническая грамматика), `status`, `provenance`; парсер отдаёт `provenance = "machine-extracted"` и `status = "unverified"` (`edition = "unverified"` до сверки); внутренний id `13.8#1` уходит в отдельное поле payload (`formula_id`) вне `NormRef`; `designation` переименовываю в `document`; пропуски становятся литералом `unverified` (не пустой строкой); поля `NormRef` фиксируются в спеке, конфиг выбирает только доп. поля. (Замечание 9, пустая `unit`: оставляю видимой как пропуск; инженер заполняет до регистрации типа.)

### 2. Откуда движок берёт формулы?

По задаче 4.1 контракта backend вызывает `search.query(...)` и связывает `symbols[].id` в
движке. В `calculation-core-contract` движок — чистая функция, которая получает от
вызывающего уже разрешённые параметры, а слой параметров — единственная точка входа
значений в движок (твой ответ 2). Это же открытый вопрос «формулы в YAML или в коде»
(задача 7.2 `calculation-core-contract`, WP5).

- **Предложение.** Пайплайн кладёт формулы в `dec_normatives`; слой параметров читает их,
  применяет фильтр по `provenance` и передаёт разрешённые параметры в движок. Backend не
  импортирует код пайплайна, зоны остаются раздельными.
- **Реестр формул.** По твоему журналу (записи 20–21) путь MVP для формул — реестр
  `normatives_pipeline/formulas.toml`, заполняемый вручную, потому что OCR формул пока
  ненадёжен. `backend-layered-architecture` планирует файлы параметров в `params/` в слое
  параметров (backend). Где лежат формулы, которые исполняет движок, и кто владелец?
- **Твоя сторона.** Согласен, или опиши путь, который ты задумывал, и назови владельца
  реестра.

**Ответ.** Согласен. Пайплайн кладёт формулы в `dec_normatives`; слой параметров читает их, применяет фильтр по `provenance` и передаёт разрешённые параметры в движок; backend не импортирует код пайплайна. Реестр `normatives_pipeline/formulas.toml` остаётся MVP-путём исполняемых выражений, владелец — я (data-зона).

### 5. Одна база данных или две?

`docker-compose.yml` поднимает одну базу PostgreSQL `dec` с одним пользователем `dec`.
`backend-layered-architecture` (решение 4) планирует две базы в одном инстансе: `dec_app`
(пользователи, расчёты, отчёты) и `dec_normatives` (документы, ревизии, пункты, формулы,
коэффициенты) с раздельными деревьями Alembic; роадмап (WP5, требование 5) добавляет
раздельные роли БД по зонам.

- **Твоя сторона.** `dec` должна стать `dec_normatives`? Может ли compose-файл создавать
  обе базы и роль на каждую зону?

**Ответ.** `dec` становится `dec_normatives`. Compose должен создавать обе базы (`dec_app` и `dec_normatives`) в одном инстансе с ролью на зону; в MVP держу `dec_normatives`, `dec_app` добавлю, когда понадобится backend'у.

### 8. API только для чтения для backend

`search.query()` на каждый вызов выполняет `db.init_schema`, то есть каждый запрос делает
`CREATE TABLE` и `ALTER TABLE`. Кроме того, `db.py` без `DEC_DATABASE_URL` молча
подключается к `postgresql://dec:dec@localhost:5433/dec`.

- **Предложение.** Изменения схемы — только при загрузке; backend получает функцию и роль
  только для чтения; отсутствие `DEC_DATABASE_URL` — ошибка, а не тихий переход на
  локальную базу.
- **Твоя сторона.** Согласен, или предложи другое разделение.

**Ответ.** Согласен. Изменения схемы — только при загрузке; backend — read-only функция и роль; отсутствие `DEC_DATABASE_URL` — ошибка, не тихий localhost.

### 9. Лексический поиск: `pg_trgm` или `tsvector`?

Запись 14 журнала выбирает `pg_trgm` для поиска в MVP, и `backend-layered-architecture`
(задача 4.3) планирует GIN + `pg_trgm`. В коде — `to_tsvector('simple', search_text)` по
заранее лемматизированному тексту.

- **Твоя сторона.** Что из этого решение? Вторую спеку нужно привести в соответствие.

**Ответ.** Решение — `pg_trgm` (запись 14). Привожу спеку и код к `pg_trgm` + GIN, убираю `tsvector`.

### 10. Локатор формулы без номера

В СП 45.13330.2017 многие формулы без номера (запись 19). Ты предлагаешь брать номер пункта
или синтетический номер. Локатор в `NormRef` не должен выглядеть как номер формулы,
напечатанный в документе (номера пунктов и формул не выдумываются).

- **Предложение.** Такую формулу указывать по её пункту в твоей канонической грамматике и
  никогда не писать номер, которого нет в документе; внутренний id, если нужен, держать
  вне `NormRef`.
- **Твоя сторона.** Согласен, или дай нужный синтаксис.

**Ответ.** Согласен. Формулу без номера указываю по её пункту в канонической грамматике, номер не выдумываю; внутренний id — вне `NormRef`.
