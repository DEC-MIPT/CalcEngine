### Блокер

- **B1. Загрузка любого другого документа переписывает каталог пилота на этот документ.**
  `ingest.py:151` вызывает `pilot_catalog.sync_pilot_catalog(conn, designation)` с

### Серьёзные

- **M1. Формула 5.7 хранится как `verified` / `human-verified`.** `ingest.py:97-98` даёт
  каждой формуле из `formulas.toml` `status = verified`, `provenance = human-verified`;
  `pilot_catalog` привязывает `5.7` оттуда. Правило идёт из задачи 1.6
  `normatives-formula-contract` («`formulas.toml` entries are `human-verified`», код в
  `0310df4`), которая попала в `develop` без ревью (M3). Это противоречит ответу Егора 2b
  (`pipeline-open-items-questions-akim.md`, «Answers»: «No pilot formula or coefficient
  gets a `human-verified` provenance») и правилу задачи 2.5, что повышение статуса —
  гейт WP3. `NormRef` backend принимает эту пару с конкретной редакцией и пунктом, поэтому
  отчёт покажет шаг R проверенным и занизит `unverified_step_count`.
  `test_status_and_provenance_on_every_view_row` проверяет только, что нет проверенной
  строки `machine-extracted`. Исправление: хранить `5.7` как `unverified` /
  `machine-extracted` (или удалить `formulas.toml`, как и планировалось) и проверять в
  тесте, что ни одна строка пилота не `verified` и не `human-verified`.
- **M2. Символ дерева без записи в обозначениях хранится как безразмерный.**
  `pilot_catalog._bind_registry_formula` переводит единицы через
  `unit_symbol(units_by_symbol.get(symbol, ""))`, а `UNIT_SYMBOLS[""] = "1"`. Символ,
  которого нет в обозначениях, получает единицу `1` вместо отказа от формулы, что
  запрещают спецификация «Expression tree form in the catalog» и задача 2.2 («a formula he
  cannot convert is not stored as bound»). На сегодняшних данных вреда нет (у всех 14
  символов `5.7` есть запись в `formulas.toml`), но недостающая единица становится
  невидимой для backend. Исправление: отказывать, если у символа дерева или символа
  результата нет записи в обозначениях; `""` -> `1` оставить только для существующей
  записи. То же касается `notation_result_symbol`, который возвращает `"R"`, если у
  формулы нет обозначений: это неявное значение по умолчанию в коде, и после исправления
  M2 та же проверка его отклонит.
  У backend зеркальная дыра (доработка Акима, не Егора): `CatalogParameterSource`
  проверяет, что у каждого символа есть единица из словаря, но не что единица символа,
  названного как вход или выход, — базовая единица этой величины (`formula_step`
  сравнивает единицы точно, поэтому совпадения размерности мало), и в решении 7 такого
  нарушения нет. Поэтому такая ошибка каталога всплывает только в `formula_step` как
  `UnitError`, который `api/errors.py` переводит в `422 invalid_input`, обвиняя клиента,

  спецификацию «Expression tree form in the catalog», а проверку — в источник на
  `feature/normative-catalog/backend` (задача 5.6). Данные пилота правилу уже
  соответствуют: все символы входов и выходов формул `5.7` и `k_z_from` в базовых единицах.

### Мелкие

- **m1. Каталог пилота записывается несколькими коммитами.** `sync_pilot_catalog`
  вызывает `delete_catalog_rows` с коммитом, затем `replace_catalog_formula` и пять
  вызовов `insert_*`, каждый со своим коммитом. Во время загрузки backend может прочитать
  пилот без строк или с половиной строк и ответить `503`; сбой посередине (таблица не
  разобралась, оборвалось соединение) оставляет пилот сломанным до следующей удачной
  загрузки СП 22. Риск небольшой: загрузка ручная и редкая. Исправление: одна транзакция
  на тип с откатом при ошибке (часть рекомендации ниже).
- **m2. Тесты каталога пайплайна идут на рабочей базе.** `test_catalog_contract.py` и
  `test_pilot_catalog.py` подключаются по `DEC_DATABASE_URL`, то есть к рабочей `dec`, без
  проверки, что имя базы кончается на `_test`. Они ставят общекластерной роли
  `dec_normatives_reader` пароль `test-reader`, поэтому на машине, где их запустили,
  пароль из `DEC_NORMATIVES_READER_PASSWORD` перестаёт работать до следующей загрузки;
  кроме того, они переписывают строки пилота и могут сами загрузить PDF. Исправление:
  отдельная база с именем на `_test` с отказом для любой другой и отдельная тестовая
  роль, как у backend (`dec_normatives_test`, `dec_catalog_test_reader`).
- **m3. `k_z_from` показывает одну формулу, а считает другую.** LaTeX —
  `k_z = \frac{z_0}{b} + 0.2`, дерево — `8/b + 0.2`. Шаг прозрачного вывода показывает
  `z_0`, а в подстановках только `b`, так что читатель не видит, откуда 8; 8 м — голое
  число без единицы, и результат верен только потому, что `b` приходит в формулу в
  метрах. Исправление: LaTeX показывает `8` (`k_z = \frac{8}{b} + 0.2`). Сделать `z_0`
  символом со своим значением и единицей потребует нового поля в `Parameters` пилота, то
  есть изменения контракта на стороне backend.
- **m4. Границы метода ссылаются не туда.** Границы `phi_II` в [0 deg, 45 deg] выведены
  из диапазона таблицы 5.5, но несут пункт `5.6.7`. Отказ по диапазону отправит инженера
  в п. 5.6.7, где диапазона нет. Запись Егора по задаче 2.5 сама говорит «clause 5.6.7,
  table 5.5». Исправление: `NormRef.clause` = `табл. 5.5`.
- **m5. У роли читателя остаётся `TEMP`.** В PostgreSQL 14 каждая роль по умолчанию
  получает `CONNECT` и `TEMP` на базу через `PUBLIC`, поэтому читатель может создать
  временную таблицу, и сценарий спецификации «The reader role cannot write» («or to create
  an object in any schema») на уровне роли не выполняется. Транзакции backend только для
  чтения это запрещают, так что практического вреда нет. Исправление:
  `REVOKE TEMP ON DATABASE dec FROM PUBLIC` при загрузке (владелец-суперпользователь
  право сохраняет) или записать как принятое отклонение.

### Рекомендация до второго типа расчёта (зона Егора, решение за ним)

Исправления B1 (вызывать `sync_pilot_catalog(conn)` без обозначения) для пилота
достаточно. На следующие типы (например, фундамент глубокого заложения и внутренний
водопровод) оно не масштабируется: в `pilot_catalog.py` жёстко заданы один тип, один
документ (`DESIGNATION`, `[document]` в `pilot.toml`), список привязок, форма таблицы 5.5
в `parse_heading_rows` и границы метода по диапазону этой таблицы. Тип может опираться на
несколько документов, и его каталог не должен зависеть от порядка загрузки документов.

Рекомендую до добавления второго типа разделить загрузку на два шага:

1. **Загрузка документа** заполняет только документный слой (`document`, `clause`,
   `formula`, `notation_entry`, `coefficient`, ...) и ничего не знает о типах расчётов,
   поэтому документы можно загружать в любом порядке.
2. **Сборка каталога типов** — отдельная команда (например,
   `python -m normatives_pipeline.catalog sync [--type <name>]`), которая также
   запускается в конце `ingest` для каждого типа, чей реестр называет загруженный
   документ:
   - один реестр на тип в зоне Егора (например, `ml/configs/types/<type>.toml`), где для
     каждого параметра названы документ, номер формулы, таблица с колонкой заголовка и
     колонками значений, пункт порога и границы метода, без значений в коде
     (спецификация «Calculation type binding by name»: «the pipeline SHALL fill it from a
     registry it owns»);
   - каждый тип пересобирается одной транзакцией (это заодно закрывает m1);
   - тип, у которого загружены не все документы, не собирается, и backend отвечает
     `503 parameter_source_unavailable` только для него (сценарий «A calculation type with
     no binding»); повторная загрузка одного документа пересобирает только типы, которые
     его называют.

Контракт чтения (`catalog_read`, решение 2) не меняется: представления уже разделены по
`calculation_type`, а `CatalogParameterSource` backend общий. Два ограничения контракта,
скорее всего, всплывут на следующих типах и потребуют отдельного изменения: формулы с
Σ/∏ (`formula-autoparse-limits-egor.md`; по подсчёту Егора, в СП 24.13330.2021 таких
формул 10, разбирается 5) и таблица с выбором по двум входам, которую решение 2 не
допускает.
