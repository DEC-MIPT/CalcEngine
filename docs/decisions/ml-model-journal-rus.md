# ML model & research journal — русская версия

Журнал разработки зоны data/ML (Egor). Одна запись на: пробинг источника, оценку/выбор
модели и проверку гипотезы (с коррекцией). Русская версия `ml-model-journal.md`.

Конвенция пометок: `[ML]` — модельные задачи (OCR/ViT, эмбеддинги, RAG-модели); без пометки —
детерминированные методы (regex/парсинг/индексы/лемматизация). Regex — НЕ ML.

## Запись 1 — Пробинг источников: режим доступа по реестрам (2026-09-27)

Проверяемые гипотезы: H1 (неоднородность реестров), H3 (обнаружение реестров).

Метод: обычный HTTPS GET (`requests`/`curl`, без браузера) к корню каждого реестра,
плюс проверка `robots.txt`/`sitemap.xml` и документации API.

| Источник | Результат | Режим доступа |
|---|---|---|
| `faufcc.ru` | Angular SPA (`<app>`, `main.*.js`); хост API `api.faufcc.ru`; `/docs` — Laravel admin-API (auth/users/roles/assets) | SPA + admin-API, **публичного реестра нормативов нет** |
| `fgiscs.minstroyrf.ru` | React SPA; `GET /api/opendata` → `application/json`, 15 датасетов (ФСНБ-2020/2022, КСР, ПССР, ценовые зоны, оплата труда…) | **чистый JSON open-data API** |
| `minstroyrf.gov.ru` | HTML (Bitrix), `sitemap.xml` | статический/HTML |
| `gost.ru` → `rst.gov.ru` | HTML, `sitemap.xml` | статический/HTML |
| `pravo.gov.ru` | `ConnectTimeout` на корне | нужен ретрай |

Вывод: open-data API ФГИС ЦС — единственный найденный чистый и легальный JSON API, но он
отдаёт структурированные сметные нормативы (ФСНБ/КСР/ПССР), а не полные тексты СП/ГОСТ с
формулами и пунктами. Тексты СП придётся брать из data-эндпоинтов faufcc SPA, minstroy
или pravo — пробовать дальше.

Решение: остаёмся на API-first. Playwright — только запасной вариант для SPA-реестров.

## Запись 2 — Коммерческие СПС (Техэксперт/Кодекс, КонсультантПлюс): B2B, лицензии, разметка

Контекст: полные тексты СП/ГОСТ циркулируют как PDF на официальных сайтах или внутри
коммерческих справочно-правовых систем (СПС). Обе названные системы — коммерческие B2B:

- **Техэксперт (Кодекс, `cntd.ru`)** — профильная система по техническим нормам
  (СП/ГОСТ/СНиП) с разметкой пунктов/формул. Интеграция/API есть, но требует платного
  корпоративного договора; контент и разметка — проприетарные.
- **КонсультантПлюс** — юридическая (менее релевантна техническим нормам). API есть,
  тоже платный, для лицензированных корпоративных клиентов.

Гипотеза (откуда берут данные): они **официальные распространители** по лицензионным
договорам с издателями/разработчиками норм (ФАУ ФЦС, Росстандарт, Минстрой и НИИ-авторы).
Получают эталонный электронный текст напрямую из первоисточника — не скрейпят PDF —
поэтому их редакции и статусы актуальны.

Гипотеза (кто делает разметку): разметка — их **редакторская работа, сделанная вручную**
методологами/редакторами (human-in-the-loop), и это ядро их IP: структурная разбивка на
пункты/таблицы/формулы/приложения, перекрёстные ссылки между пунктами и документами,
статусы актуальности, изменения и структурированное извлечение формул/таблиц.

Вывод для DEC: они размечают нормы **вручную**; DEC автоматизирует тот же шаг
(NLP/RAG-парсинг + верификация с человеком в контуре). Эта автоматизация — дифференциатор
и тезис. Коммерческие СПС — юридическая/коммерческая зависимость (C5); исключены из MVP.
Бесплатные официальные источники (PDF + API pravo.gov.ru + open-data fgiscs) — путь MVP.

## Запись 3 — pravo.gov.ru: полный документированный REST API (подтверждено)

`pravo.gov.ru` (Официальный интернет-портал правовой информации) отдаёт бесплатный,
документированный OpenAPI/Swagger-сервис на `http://publication.pravo.gov.ru/`
(`swagger/v1/swagger.json`, заголовок `Architect.Public.OpenApi`). Ключевые эндпоинты:

- `GET /api/Documents` — поиск по `Name`, `Number`, `EoNumber`, `DocumentText`, диапазонам
  дат; возвращает `items[]` с `eoNumber`, `title`, `number`, `documentDate`, `pagesCount`,
  `pdfFileLength`, `documentTypeId`, `signatoryAuthorityId`, `id`.
- `GET /api/Document?eoNumber=` — метаданные.
- `GET /api/DocumentText?eonumber=` — полный текст.
- `GET /{controller}/pdf/{eoNumber}` — скачивание PDF.
- `GET /OpenData/*` — открытые данные CSV (governmentauthority, legalacts).

Зафиксированные нюансы: HTTPS к хосту таймаутит из этой среды (HTTP работает); `PageSize`
принимает только конкретные значения (30/100/200 — 5/20/50 отклоняются с RFC 7807).

Вывод: этот API индексирует **правовые акты** (законы, приказы, постановления) — не
технические тексты СП. `Name=22.13330`, `Name=свод правил`, `DocumentText=22.13330` — все
возвращают 0 записей. То есть формул/пунктов СП здесь нет; они лежат как PDF на
faufcc/minstroy.

Заключение: подтверждены два бесплатных рабочих JSON API (open-data fgiscs для
структурированных сметных норм, pravo для правовых актов с текстом+PDF). Технические
тексты СП остаются только в PDF — коллектору нужен путь скачивания PDF для СП из
faufcc/minstroy в дополнение к двум API.

## Запись 5 — Историческая прослеживаемость нормативов = киллер-фича (CustDev)

Инсайт из CustDev (от разработчика): респонденты испытывают трудности с поиском СТАРЫХ
версий нормативных документов. Пример сценария — «как считалось здание/сооружение,
построенное в 1985 году? По каким нормам, какие коэффициенты тогда действовали?».

Это делает **исторические редакции** требованием первого класса для коллектора, а не
«приятным дополнением»: сервис должен резолвить нормативную базу на любую прошедшую дату,
а коллектор — вносить устаревшие редакции аддитивно (сходится с WP3 «аддитивное хранение
редакций» и решением о неизменяемости `NormRef`).

Результат пробинга: ни один реестр faufcc не отдаёт исторические редакции. Соседний реестр
`reestr-normativno-tekhnicheskoi-dokumentatsii` (id реестра
`b154aaa9-236f-4c4d-8f2c-fab07558f322`) возвращает записи с `number=null` и без ссылки на
файл `asset` — только метаданные, только текущие документы. Старые СНиП 1980-х
(СНиП 2.02.01-83, СНиП 2.04.01-85 и т.д.) в бесплатных официальных реестрах отсутствуют.

Открытый вопрос: где живут исторические/утратившие силу редакции? Кандидаты: коммерческие
СПС (Техэксперт хранит исторические версии), архивные сканы или архивы утверждающих
органов. Нужна отдельная стратегия источника, прежде чем фичу «поиск на 1985 год» можно
будет питать данными.

## Запись 6 — pravo (приказы) и Техэксперт (docs.cntd.ru): результаты пробинга

pravo.gov.ru:
- `SignatoryAuthorityId=efa6da4b-…` (Минстрой России) работает — 899 приказов, но они
  административные (формы, порядки, перечни). `Name=22.13330`, `Name=утверждении свода
  правил`, `DocumentText=свод правил` → 0. То есть приказы об утверждении СП на pravo не
  всплывают (портал индексирует правовые акты, а не хронологию СП). pravo — не источник
  редакций СП или их статусов.

Техэксперт (`docs.cntd.ru`):
- Nuxt SSR-приложение. `robots.txt`: `Disallow: /api`, `Disallow: /search?`, `Disallow:
  /purchased`. Sitemaps: `/pages.xml`, `/sitemap/docs/documents_sitemap.xml`.
- Их `/api` существует, но явно запрещён для краулеров; программный доступ — нарушение
  ToS/копирайта. Контент коммерческий.

Ответ на «откуда Техэксперт берёт документы»: они официальные распространители по
лицензионным договорам с ФАУ ФЦС / Росстандарт / Минстрой и получают эталонные
электронные тексты напрямую из систем издателей — не через публичный канал. Этот канал
нам недоступен без собственных договоров.

Итог для коллектора: бесплатные официальные источники покрывают текущие СП (API faufcc),
структурированные сметные нормативы (open-data fgiscs) и правовые акты (API pravo).
Исторические редакции СНиП/СП **не имеют бесплатного официального источника** —
коммерция (Техэксперт) или архивные сканы. Это жёсткая граница для киллер-фичи
«поиск на 1985 год»; нужно решение (коммерческий договор vs загрузка архивных сканов vs
отложить).

## Запись 7 — Техэксперт: с кем договоры (кандидаты для переговоров)

Техэксперт (Консорциум «Кодекс») — официальный распространитель; договоры с
правообладателями нормативных документов:

- **Росстандарт** (Федеральное агентство по техническому регулированию и метрологии) —

## Запись 9 — Распространение ошибок в ML/OCR на нормативных источниках (научная заметка)

**Тезис.** Машинно извлечённый текст (OCR архивных сканов, затем NLP/RAG-извлечение
формул, коэффициентов и пунктов) несёт неустранимую, ненулевую ошибку, которая
распространяется в расчёт. Поэтому извлечённый слой следует считать недоверенным
(`machine-extracted`, `unverified`) до верификации человеком; движок детерминирован и
принимает только `human-verified` значения («нет ML в расчётном пути»).

**Почему возникает ошибка.**

1. *Деградация источника.* Архивные СНиП — сканы бумаги: низкое разрешение, выцветшие
   чернила, перекос, пятна, неравномерная освещённость. Типографика 1980-х (фотонабор,
   многоколоночные таблицы, под-/надстрочные индексы, сноски) далека от чистого входа для
   OCR.
2. *Сложность доменных символов.* Инженерные нормы смешивают кириллицу/латиницу/греческий
   и математическую нотацию (N₀, R₀, γ_c, φ_II, 10⁻³). Общие OCR-модели, обученные на
   естественном тексте, ошибаются именно на этой смешанно-символьной, насыщенной
   формулами поверхности.
3. *Систематические режимы ошибок.* Путаница гомоглифов (0/O, 1/l, З/3, К/K), сплющивание
   под-/надстрочных индексов (N₀ → N0 / NO), неверное распознавание формул (математика —
   это задача layout'а, а не символов) и ошибки сегментации ячеек таблиц. Критичные
   токены — цифры, индексы, единицы — именно там, где концентрируется ошибка.
4. *Каскадирование.* Ошибка OCR → ошибка извлечения → неверный коэффициент → неверный
   результат. Одна неверно прочитанная цифра меняет расчётное значение; ошибки
   умножаются по цепочке.

**Как можно пытаться исправить (инструменты).**

- *OCR:* Tesseract (базовая линия, слаб на кириллических формулах); Surya / PaddleOCR
  (мультиязычные, лучше на документах); ABBYY FineReader (коммерческий, лучший на русском
  инженерном тексте); формульно-специфичные: Nougat (Meta), MathPix, pix2tex/LaTeX-OCR.
- *Layout/таблицы:* Table Transformer, PP-Structure, LayoutLM.
- *Пост-коррекция:* LLM-пересчёт контекста по доменному глоссарию (обозначения, единицы),
  правило-основанная нормализация обозначений и единиц.
- *Маршрутизация/ансамбли:* уверенность OCR для отправки низкоуверенных фрагментов на
  ревью; голосование нескольких движков.

**Почему полное исправление практически недостижимо.**

1. *Неустранимая потеря информации.* Ниже порога качества глиф физически отсутствует в
   изображении; никакая модель не восстановит информацию, которой нет.
2. *Перцептивная ≠ семантическая точность.* OCR оптимизирует CER/WER, но корректность
   здесь семантическая (1.2 vs 12; индекс vs множитель). Высокая символьная точность
   может сосуществовать с неверными значениями, а у модели нет понятия инженерного смысла.
3. *Распознавание формул остаётся открытой задачей.* Даже state-of-the-art
   (Nougat/MathPix) ошибается на нестандартных layout'ах; один неверный индекс меняет
   смысл формулы.
4. *Нет разметки (ground truth) в масштабе.* Верификация требует эталонного текста — ровно
   того, чего нет для архивных сканов — поэтому остаточную ошибку нельзя ни измерить, ни
   надёжно исправить.
5. *Концентрация ошибки на «полезной нагрузке».* Метрики выглядят приемлемыми в агрегате,
   а критичные токены (цифры/индексы/единицы) систематически неверны — длиннохвостовый,
   состязательный профиль.
6. *Плохая калибровка.* Оценки уверенности ненадёжны при доменном сдвиге.

**Следствия (добавлено).** Гейт «человек в контуре» — архитектурный инвариант, а не
заплатка: вывод ML — черновой помощник (подсказка + ссылка на источник), а не источник
истины. Коммерческие СПС избегают OCR вовсе, получая эталонные электронные тексты от
издателей; наша фича исторической прослеживаемости загоняет нас в OCR ровно там, где
потолок ошибок максимален — это настоящий компромисс уровня тезиса, который надо
проговаривать и мерить, а не прятать. Практическая политика: для базовой линии
предпочитать цифроворожденные документы (нативный текстовый слой, напр. текущие СП из
faufcc); оставить OCR для исторического трека; отчитываться об остаточной ошибке по типу
сущности (CER / F1 извлечения / exec_rate) и проводить каждое машинно выведенное значение
через гейт `human-verified`.

## Запись 13 — Парсер: baseline и формула → код (первые прогоны)

Прогон на пилотном СП 22.13330.2016 (222 стр., text-PDF):
- слой — text (не скан); пунктов — 647 (regex); номеров формул — 124; записей обозначений —
  729; таблиц — 1 (из первых 15 стр., для скорости).

Формула (5.7) → исполняемый код:
- **надёжное** (явная таблица символов + детерминированное выражение) → `lambdify` →
  R = 143,75 кПа. Работает.
- **менее валидное** — наивный `parse_latex`: тихая ошибка — `\gamma_{c1}` → `c*1`,
  `\gamma_{II}` → `I*I` (мнимая единица в квадрате). Подтверждает доменный сдвиг (H9/H10):
  многосимвольные/римские индексы русской нотации наивный LaTeX-парсер ломает.
- Вывод: надёжный путь — НЕ наивный `parse_latex`, а явная таблица символов (или
  структурированный AST), т.к. индексы нужно маппить осознанно.

Производительность / формат:
- pdfplumber `extract_text` — 60 с на 222 стр.; `pdftotext` (poppler) — ~1 с. Текст берём
  через pdftotext (subprocess), pdfplumber — только для таблиц (и те медленно, ~0,23 с/стр.
  → нужна точечная выборка страниц с таблицами).
- Текстовый слой формулы искажает: греческие буквы/индексы в pdftotext становятся
  квадратиками (, ). Поэтому извлечение формул из текстового слоя ненадёжно — нужен
  image-OCR (pix2tex) или явная таблица символов.

## Запись 14 — RAG: сравнение эмбеддингов vs TF-IDF (recall@k на пунктах СП)

Корпус: 635 пунктов СП 22.13330.2016 (текст > 30 симв.). 5 ground-truth запросов
(естественная фраза → номер пункта). Метрика recall@1/3/5 (точное совпадение номера).

| Модель | recall@1 | recall@3 | recall@5 |
|---|---|---|---|
| cointegrated/rubert-tiny2 (312-dim) | 20% | 20% | 20% |
| intfloat/multilingual-e5-small (384-dim) | 60% | 60% | 60% |
| TF-IDF (лексический baseline) | 60% | 60% | 60% |

Выводы:
1. rubert-tiny2 слишком слаб для этой задачи (20%) — крошечная модель, 312 измерений.
2. multilingual-e5-small дотягивает до TF-IDF, но НЕ обходит лексический baseline.
3. Для точных запросов (реальный кейс поиска нормативов) лексический поиск (pg_trgm/TF-IDF)

Ограничение: eval использует точные запросы (в пользу лексики). Для честной оценки
семантики нужны парафраз-запросы + отдельный ground-truth (следующий шаг).
Решение: MVP-поиск — лексический (pg_trgm); эмбеддинги подключать как семантический слой
поверх (гибрид) с более сильной моделью или файнтюном.

## Запись 15 — NLP: pix2tex на формуле (5.7) — доменный разрыв (OCR)

Контролируемый тест: формула (5.7) отрисована в изображение (matplotlib), прогнана через
pix2tex (ViT, обучен на английской академической математике).

Вход: `R = \frac{\gamma_{c1}\gamma_{c2}}{k}[M_\gamma k_z b \gamma_{II} + M_q d_1 \gamma'_{II} + (M_q-1)d_b\gamma'_{II} + M_c c_{II}]`

Выход pix2tex:
`R = \frac{\underline{v_{c1} y_{c2}}}{k}[M_\gamma k_z b V_{II} + M_q q_1 V'_{II} + (M_q-1)d_b V'_{II} + M_c C_{II}]`

Ошибки:
- греческая γ распознана как v/y/V (три разных латинских!) — `\gamma_{c1}→v_{c1}`,
  `\gamma_{c2}→y_{c2}`, `\gamma_{II}→V_{II}`;
- `d_1 → q_1`; `c_{II} → C_{II}` (регистр); лишний `\underline{}`.
- НО структура сохранена: дробь, скобки, индексы, штрихи — корректно.

Вывод: pix2tex сохраняет структуру формулы, но ломает греческие символы (γ→v/y/V) и
регистр. Для русских инженерных формул нужен пост-корректор символов (маппинг γ↔v/y/V,
нормализация регистра) или дообучение на домене. Подтверждает H9/H10.

## Запись 16 — RAG: ё-нормализация обязательна

Тот же запрос с «ё» и без «ё» на корпусе из 647 заголовков пунктов СП 22.13330.2016:

- `расчётные значения характеристик грунтов формула` → 0.704 (5.3)
- `расчетные значения характеристик грунтов формула` → 0.835 (5.3)

Падение ~16% только из-за ё/е: TF-IDF токенизатор считает «расчётные» и «расчетные»
разными токенами, в совпадении остаются только общие слова («значения», «характеристик»,
«грунтов»), что снижает косинус. Пользователь обычно пишет «е» (без ё), а в нормах «ё»
встречается редко и непоследовательно.

Правило (обязательно для всего поиска, лексического и эмбеддингов):
- нижний регистр;
- ё → е (и запрос, и документ);
- вычистить replacement-символы (□) из текста перед индексацией.

## Запись 17 — RAG: индексация формул + лемматизация (морфология)

Сырой текст формулы бесполезен (квадратики). Формулы индексируются как отдельные
элементы с «обогащённым» search_text = `формула <N>` + заголовок пункта + смыслы
обозначений со страницы (+ latex). Привязка формула→пункт — по `(page, line)`:
формуле назначается ближайший предшествующий заголовок пункта на той же странице.

Без лемматизации запрос `расчётные значения характеристик грунтов формула` не выводил
формулу (5.1) в топ: «расчетные» (запрос) ≠ «расчетных» (в заголовке 5.3.16), поэтому
косинус падал. С pymorphy3 (лемматизация) формула (5.1) стала первой:

- формула 5.1 (пункт 5.3.16) — 0.435; дальше 6.41, 6.42, 6.43, 5.33.
- пункты: 5.3 / 5.3.15 / 5.3.2 — корректно.

Вывод: для русского поиска нужна лемматизация (морфология), а не только ё-нормализация;
иначе словоизменение («расчетные/расчетных/расчетными») ломает точность. Формулы должны
быть отдельными элементами индекса, связанными NormRef с пунктом.

## Запись 18 — RAG: чтение PDF на каждый запрос само по себе медленно (скорость/удобство)

Текущий демо-поиск на каждый запрос заново читает PDF (`pdftotext`), заново извлекает
пункты/формулы/обозначения, заново лемматизирует ~1400 текстов (pymorphy3) и заново
собирает TF-IDF. Узкое место — не сам ранжирующий поиск, а именно «прочитать и
обработать документ» на каждый запрос: это противоречит требованию мгновенного отклика.

Относится к гипотезе о скорости и удобстве: рабочая гипотеза паспорта (лист 3, A92) —
«сократить время типового расчёта с 2–4 часов до 20 минут», критерий приёмки пайплайна —
«подгрузка < 2 сек»; боль инженера из проблемных интервью — «поиск актуальной редакции
нормы до 30–40 мин».

Вывод: поиск обязан работать поверх **заранее подготовленного** хранилища (структуры +
индекс, собранные в офлайн-ingestion при получении документа), а на запрос выполнять
только нормализацию+лемматизацию строки запроса и lookup в готовом индексе. Читать PDF в
момент запроса нельзя — это и есть причина «работает долго».

## Запись 19 — H4/H10: СП 45.13330.2017 — формулы БЕЗ номеров

Запрос «условие успешного погружения опускных колодцев» нашёл пункт 13.8, но формулу не
вывел и «где…» не расписал. Причина — в самом документе формула не пронумерована:

```
13.8 Для успешного погружения опускных колодцев должны соблюдать следующее условие:
    G + Gп ≥ КпΣТ,
где G – собственный вес колодца (с учетом взвешивания в воде);
    Gп – дополнительная пригрузка колодца;
    Кп = 1,15–1,25 – коэффициент условий работы при погружении;
    ΣТ – силы трения стен колодца по грунту.
```

Нет маркера `(13.x)` в конце строки. Извлекатель формул завязан на `(N.N)` → по всему
документу совпало 1 строка → «формул 1». Блок «где…» в `extract_formula_notation` тоже
привязывается только к найденным (пронумерованным) формулам, поэтому он пропал.

Сравнение: в СП 22.13330.2016 формулы пронумерованы `(5.1)`, `(5.7)`; в СП 45 — часто
без номера, инлайн. Подтверждает H4 (неоднородность форматов) и H10 (нужны адаптеры на
документ, один универсальный парсер не работает).

Направление фикса: детектировать формулу по структуре (строка-формула + следующий блок
«где…»), а не по номеру; как номер брать номер пункта или синтетический.

## Запись 20 — H5/H6: текстовый слой непригоден для математики

Проверка формулы (5.7) в СП 22.13330.2016 — `pdftotext -layout` даёт фрагментированную
раскладку, где числитель/индексы/знаменатель разбросаны по строкам, а греческие закодированы
PUA-глифами:

    26: '              \uf067 \uf067'                 # γ γ (числитель)
    27: 'R = c1 c2 \uf05bM k b\uf067 + M d \uf067\uf0a2 + (M − 1)d \uf067\uf0a2 + M c \uf05d,'   # тело + c1,c2
    28: '(5.7)'
    29: '\uf067 z \uf049\uf049 q 1 \uf049\uf049 q b \uf049\uf049 c \uf049\uf049'  # индексы γ,z,II,q,1,II,q,b,II,c,II
    30: 'k'                                      # знаменатель

## Запись 21 — OCR (pix2tex) на реальной формуле: провал на этом PDF

Рендер области формулы (5.7) → pix2tex (две попытки, разные кропы, 300 и 400 dpi) даёт мусор:
модель читает окружающий текст («При расчете деформаций…») как таблицу, а не формулу. На
синтетическом чистом рендере (Запись 15) структура сохранялась; на реальном деградированном
PDF (PUA-шрифты, смешение с заголовком) — провал.

Вывод для MVP: автоизвлечение `expression` из ЭТОГО PDF через pix2tex нестабильно. Путь MVP =
детерминированный **реестр формул** (`formulas.toml`): выражение+latex+символы задаются один
раз точно (0 ошибок), пайплайн доставляет их автоматически. OCR (Nougat/MathPix, лучший рендер)

## Запись 22 — OCR: двухстадийный пайплайн (детекция + распознавание) — структура читается

Собрал декомпозированный двухстадийный пайплайн (отдельные модули + отдельный конфиг
`ocr.toml`): (1) `ocr/detect.py` — детекция области формулы по координатам символов (маркер
`(N.N)` + x-фильтр отступа), (2) `ocr/recognize.py` — pix2tex по чистому кропу.

Результат на (5.7) из реального PDF: **структура формулы восстанавливается** —
`R=\frac{...}{...}[M_\gamma b + M_q d \gamma' + (M_q-1)d c]` (дробь, скобки, индексы, штрихи).
Но: (а) детекция всё ещё захватывает инлайн-заголовок «…вычисляемого по формуле» (формула
стоит вплотную к тексту), (б) символы искажены (γ→`*`, k→`L`, II→`1`, b→`b1`, d_b→`d_c`,
c_II→`c_n`).

Вывод: CNN/ViT-путь работает на **структуру**. Для точного `expression` нужны (1) точная
детекция (отделить инлайн-заголовок) и (2) пост-коррекция символов / дообучение. Подтверждает
H9: чистая автоматика без человека не даёт 99,9%.

## Запись 26 — [ML: мелкие локальные LLM] не заменяют OCR; годятся для «текст → структура» и разметки

Оценка мелких локальных LLM (`Qwen2.5-3B`, `Llama-3.2-3B`, `Gemma-2-2B`) под задачу чтения формул:

структурно-ограниченным JSON-выводом.
