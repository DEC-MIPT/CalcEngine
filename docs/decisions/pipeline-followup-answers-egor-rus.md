## A. pipeline-followup-questions

### A1. Write-путь для `status`/`provenance`

Ручная верификация каждой формулы нереалистична: в одном документе порядка 96
формул, на корпус это тысячи. У меня нет ни времени, ни желания верифицировать
каждую индивидуально.

Предлагаю зашить во фронт и бэк механизм из одной кнопки: у показанной формулы
пользователь видит вопрос «Эта формула НЕ КОРРЕКТНАЯ? → Да». Так корректность
тестируется на реальном пилоте, и пользователи сами укажут, где верно, а где нет.
Для этого предусмотреть сбор статистики по каждой формуле: N раз показана, N раз
отмечена как некорректная. Порог «сколько флагов = формула реально некорректна»
решим позже по собранной статистике.

Если этот механизм не принимается, я сделаю обратное — механизм, который всем
формулам автоматически пропишет «Проверена, верна», и руками верифицировать не буду.

Граница ответственности: механизм смены флага (кнопка → запись в БД) живёт в бэкенде
Акима. Я только инициализирую и наполняю БД, читает её Аким. В код Акима я не лезу.
Схема с колонками `status`/`provenance`/`shown_count`/`flagged_count` — моя, эндпоинт
и кнопка — Акима.

### A3. `formulas.toml` и `human-verified`

`formulas.toml` создавался как тестовый реестр — эталон, с которым мы сверяли формулы,
извлечённые CNN. Он не задумывался как постоянное хранилище, и его нужно удалить, а не
поддерживать: если заносить туда записи хотя бы для десяти СП, файл станет неоправданно
раздут. Поэтому отдельное решение о семантике `human-verified` для этого файла не
требуется: реальная семантика задаётся на уровне схемы БД и пайплайна (см. A1).
