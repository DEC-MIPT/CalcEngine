# Журнал research (ноутбук извлечения формул)

Лабораторный журнал по `research.ipynb`: рендер страниц PDF в изображения и чтение
формул предобученными моделями. Русская версия (англ. зеркало: `research-journal.md`).

Конвенция тегов: `[ML]` — модельные задачи (детекция/OCR); без тега — детерминированные
методы (рендер, кроп, ввод-вывод).

## Запись 1 — Рендер страниц в изображения (2026-09-27)

Метод: pdfplumber `page.to_image(resolution=300)` → один PNG на страницу, сохранение в
`normatives_pipeline/research/pages/page_NNN.png` (222 страницы для СП 22.13330.2016).

Вывод: pdfplumber корректно растеризует на 300 dpi (2482×3507). Изображения сохраняются
на диск, а не в память (222 страницы — это ~5 ГБ в RAM).

## Запись 2 — [ML] Детекция формулы моделью DocLayout-YOLO (2026-09-27)

Метод: DocLayout-YOLO (YOLOv10, предобучена на DocStructBench), класс `isolate_formula`,
imgsz=1024, conf=0.25, на странице 38.

Вывод: формула детектится и вырезается
(`normatives_pipeline/research/crops/page_038_formula_0.png`). HF-репозиторий
`juliozhao/DocLayout-YOLO-DocStructBench` напрямую в `YOLOv10(...)` не резолвится — нужно
скачать `doclayout_yolo_docstructbench_imgsz1024.pt` через `hf_hub_download` и передать
локальный путь.

Заключение: детекция работает из коробки; для bbox берём DocLayout-YOLO, дообучение не нужно.

## Запись 3 — [ML] Распознавание LaTeX моделью texify — НЕУДАЧА (2026-09-27)

Метод: `texify` (Donut-based vision-encoder-decoder), `load_model()` + `load_processor()`
+ `batch_inference` на кропе страницы 38.

Вывод: падает с `AttributeError: 'dict' object has no attribute 'to_dict'` внутри
`TexifyConfig.from_pretrained` (transformers `configuration_utils.to_diff_dict`). Причина:
transformers 4.57.6 несовместим с кастомным config-классом texify 0.2.1.

Дальше: зафиксировать совместимую версию transformers, либо перейти на pix2text / pix2tex.

## Запись 4 — Выбор датасета для распознавания формул (2026-09-27)

Решение: im2latex-230k как bulk-база для fine-tune (Zenodo 7738969,
`PRINTED_TEX_230k.zip`, ~1 ГБ): `generated_png_images/` + `final_png_formulas.txt`
(+ `230k.json` словарь). Чистые векторные рендеры совпадают с нашими кропами лучше, чем
шумные сканы arXiv (UNITE/IBEM).

Оговорка: ни один публичный датасет не покрывает кириллические нормативные формулы (`c₁`,
`γ_II`, `где`-блоки), поэтому реальная доменная адаптация всё равно требует своего русского
золотого набора из СП.

## Запись 5 — Стратегия ML-пайплайна: MVP сейчас, своя модель потом (2026-09-27)

Решение (подтверждено разработчиком):

- MVP сейчас: готовая предобученная модель для распознавания формул (детекция = DocLayout-YOLO;
  распознавание = texify/pix2text, без обучения). Готовое решение, без fine-tune в MVP-пути.
- Будущий ML-пайплайн: обучим свою модель распознавания на im2latex-230k, будем пополнять
  датасет своими формулами (русский золотой набор из СП) и повторно дообучать модель по мере
  роста датасета (цикл: собрать → расширить → дообучить).

Таким образом, скачивание датасета (`research.ipynb`, ячейка 4) — задел под будущий пайплайн,
а не часть поставки MVP.

## Запись 6 — [ML] Распознавание формул: pix2text LatexOCR работает (2026-09-27)

Вывод: texify (запись 3) по-прежнему несовместим с transformers 4.57.6. `LatexOCR` из pix2text
(`mfr-1.5`, ONNX-бэкенд) работает из коробки на CPU (в onnxruntime нет CUDA-провайдера).

Результат на кропе стр. 38: score=0.979, LaTeX
`\Delta h \leq a ~ ( \mathrm{t g} ~ \varphi_{\mathrm{I}} + c_{\mathrm{I}} / p ),`.
Известные огрехи постобработки: `\mathrm{t g}` должно быть `\mathrm{tg}`, лишние `~`.

Заключение: для MVP используем pix2text LatexOCR (device="cpu"); texify отложен до безопасного
пина transformers.

## Запись 7 — sklearn-пайплайн + оценка на валидации (2026-09-27)

Собран исследовательский пайплайн как scikit-learn `Pipeline` (детекция → распознавание →
коррекция) и валидационный набор (`research/validation.toml`, 3 проверенных эталона: 5.1, 5.5,
5.7). Метрика: нормализованная близость по редакционному расстоянию (difflib ratio после
канонизации LaTeX).

Первый прогон: средняя близость 0.764 — 5.5 (простая) 0.939; 5.1 0.682; 5.7 (сложная
R-формула) 0.671. Слабое место: сложные индексы — `\gamma_{II}` → `\mathrm{\tiny I I}`,
`k_z` → `k_{\varepsilon}`. Это ровно то, что должен чинить fine-tune + золотой набор (запись 5).

## Запись 8 — Семантическое сравнение формул через latex2sympy2 (2026-09-27)

Строковая близость difflib (запись 7) штрафовала за косметику LaTeX (`\big` vs `\left`,
двойные индексы `_{_{\gamma}}`, `\mathrm{I}` vs `I`, лишние `{}`). Заменил на семантический
круг: лёгкая предобработка (`normalize_latex`) → `latex2sympy2` → равенство SymPy-выражений.

Результат: формулы 5.5 и 5.7 теперь `equal=True` (точное семантическое совпадение), а не
0.939/0.671. `sympy.parse_latex` здесь непригоден — ломает `\mathrm{tg}` → `g*t`,
`\mathrm{I}` → `I*mathrm`, `\gamma_{II}` → `gamma_{I*I}`; `latex2sympy2` это делает верно
(держит `\mathrm{tg}` символом, сохраняет многосимвольные индексы).

## Запись 9 — Разрешение зависимостей: один antlr4, выбросить мёртвый груз (2026-09-27)

`latex2sympy2` требует `antlr4==4.7.2`, что конфликтует с `omegaconf` (4.9, через text-OCR
pix2text) и `sympy.parse_latex` (4.11). Решение без отдельного venv и без потери качества:

- убрал `sympy.parse_latex` (`alternative_parse_latex` в `formula_code.py` — «менее валидный»
  путь; MVP идёт через детерминированный реестр, не `parse_latex`);
- убрал `texify` (уже сломан на transformers);
- обошёл `omegaconf`: импортирую `pix2text.latex_ocr.LatexOCR` напрямую (небольшой shim), а не
  `from pix2text import LatexOCR` — `latex_ocr.py` нужен только `cnocr.utils`, а не text-OCR
  цепочка, тянущая `omegaconf`.

Итог: один antlr4 (4.7.2); работают и `LatexOCR` (mfr-1.5), и `latex2sympy2`. Плюс поднял
рендер страниц с 300 до 400 dpi — там распознавание отличное.

## Запись 10 — Смена направления: OCR заполняет, реестр верифицирует (2026-09-27)

Запись 21 ML-журнала объявила ручной реестр (`formulas.toml`) путём MVP по формулам, потому что
pix2tex был нестабилен. Теперь направление обратное: research-OCR (pix2text mfr-1.5 +
DocLayout-YOLO + DPI 400) читает формулы хорошо — пилоты 5.5 и 5.7 совпадают семантически без
ошибок, — поэтому авто-извлечение масштабируется, а ручное заполнение реестра на сотни формул
нереально.

Новая модель:
- OCR — основной источник: заполняет `latex` (и кандидатный `expression`) для каждой формулы с
  `provenance=machine-extracted`, `status=unverified`;
- реестр — проверенное подмножество: в него входят только формулы, которые должны быть точны
  на 100%.

Поток верификации (открытый вопрос Акиму, `formula-verification-akim.md`): на стороне
пользователя инженер видит выдержку из норматива + извлечённый LaTeX + обозначения и отмечает
«верно»/«косяк» (при косяке — правит). На пилотах косяков не было.

## Запись 11 — Решение: детекция CNN + распознавание pix2text (2026-09-27)

Почему именно так. PDF текстовые (не сканы), поэтому символы есть в текстовом слое — но
СТРУКТУРА формулы (дроби, индексы, степени) закодирована только позицией символов и размером
шрифта, а не в тексте (ML-журнал, запись 20). Два варианта:

1. Координатная реконструкция (детерминированная): группировка символов по базовой линии,
   детекция индексов/степеней по размеру и смещению, дробей — по числителю/знаменателю.
   Пробовал как `parser/formula_layout.py` — первая версия путала индексы (`^{c}` вместо
   `_{c1}`), пропускала дроби и прихватывала блок «где». Доводить — значит писать хрупкий
   layout-движок.
2. Детекция CNN + распознавание OCR: DocLayout-YOLO (предобучена на DocStructBench) находит
   bbox формулы на отрендеренной странице (DPI 400); pix2text (LatexOCR mfr-1.5, ONNX)
   восстанавливает LaTeX-структуру из этого кропа. Это и валидировал research-ноутбук — пилоты
   5.5 и 5.7 совпадают семантически через `latex2sympy2`.

Решение: вариант 2. CNN надёжно находит позицию (без координатных эвристик), pix2text надёжно
восстанавливает структуру (без хрупкого layout-движка). Цена: ML (CPU ONNX, ~5 с/формула) и
статус `machine-extracted`/`unverified` — принимаем, потому что верификация пользовательская
(`formula-verification-akim.md`). Параметры (DPI 400, conf 0.25, imgsz 1024) лежат в
`parser.toml` `[formula_ocr]`. Пакет `ocr/` и `ocr.toml` удалены; пайплайн —
`normatives_pipeline/formula_ocr.py` (детекция + распознавание + `correct_latex`).

## Запись 12 — Жизненный цикл моделей: ленивые синглтоны + прогрев (2026-09-27)

Что: `formula_ocr.py` грузит DocLayout-YOLO (детектор) и pix2text (распознаватель) лениво, как
модульные синглтоны (`_get_detector` / `_get_recognizer`), плюс `warm_up()`, который форсирует
обе загрузки.

Почему: модели тяжёлые (веса + ONNX-сессия); грузить их на каждый вызов/формулу нельзя.
Синглтон грузит один раз за процесс; `hf_hub_download` кэширует веса на диске (HF-кэш), поэтому
повторной загрузки нет.

Зачем: долгоживущий сервис вызывает `warm_up()` при старте — первый запрос уже тёплый; батч-CLI
(`enrich.py`) амортизирует ту же разовую загрузку на весь документ.
