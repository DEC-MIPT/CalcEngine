## 1. Формулы как деревья выражений (решение 11 WP2)

Требование `backend-layered-architecture` «No hardcoding» запрещает писать формулу или
коэффициент литералом в коде или в `.yaml`, а `formulas.toml` удалён. Значит, движок не может
держать формулу пилота в виде Python-кода, и разбирать строки формул тоже не должен
(`sympify`, `parse_expr` и `lambdify` исполняют код; раздел «Risks» WP2).

- **Решение (моё, для бэкенда).** Код типа расчёта хранит только порядок метода: какая
  формула, какое табличное значение, какая ветка, какая проверка. Арифметику выполняет
  интерпретатор дерева выражения, которое приходит вместе с resolved parameters.
  Допустимые узлы: `number` (константа, напечатанная в формуле), `symbol`, `add`, `sub`,
  `mul`, `div`, `pow`, `neg` и `call` функции из закрытого списка (первый список: `sqrt`,
  `exp`, `ln`, `log10`, `sin`, `cos`, `tan`, `abs`, `min`, `max`; функция добавляется, только
  когда она нужна формуле типа из in-scope списка); глубина дерева не больше 64, узлов не
  больше 4096. Движок проверяет всё дерево до вычисления; всё остальное — ошибка, ничего не
  исполняется. Пороги, выбирающие ветку метода, если их даёт норма, тоже приходят данными,
  каждый со своим `NormRef`.
- **Что нужно от тебя.** Для каждой сохранённой формулы, рядом с её LaTeX и `NormRef`:
  (a) дерево выражения в JSON с этим набором узлов, построенное при загрузке (`latex2sympy2`
  у тебя уже есть, так что перевод LaTeX в дерево остаётся в твоей зоне); (b) привязка
  каждого символа формулы к величине с единицей (в твоём `NotationEntry` есть `symbol`,
  `meaning`, `unit`).
- **С твоей стороны.** Согласиться или предложить другой формат дерева. Точную форму JSON
  можно зафиксировать вместе в `normative-catalog-backend` (пункт 5).

## 3. Честный `NormRef.status` (резолюция 2 WP2, дополнение)

В `pipeline-followup-answers-akim.md`, A1, я просил тебя автоматически отмечать все формулы
как проверенные. Сверив это со спеками, я оставляю автоматическую отметку, но в
`NormRef.status` она не попадает:

- `status = verified` сохраняет смысл требования WP1 «Norm reference status»: человек сверил
  ссылку с первоисточником. `NormRef` с `provenance = machine-extracted` всегда имеет
  `status = unverified`; бэкенд проверяет это, когда строит `NormRef`, какая бы отметка ни
  стояла в твоей строке.
- На MVP слой параметров не отвергает значения `machine-extracted`. Они доходят до движка,
  каждый шаг, который на них опирается, помечается непроверенным и учитывается в
  `unverified_step_count` (сценарий WP1 «Unverified norm source»). Иначе ни один расчёт не
  запустится.
- **С твоей стороны.** Подтвердить. Для твоей схемы это значит: `provenance` должен быть
  честным (`machine-extracted` для результатов OCR), как бы ни называлась автоматическая
  отметка; бэкенд читает `provenance`, а не отметку.

## 4. Алгоритм `input_hash` (решение 6 WP2)

Сохранённый результат будет идентифицироваться по `input_hash`, поэтому алгоритм касается
закрепления в WP3 (`norm-source-traceability`, твоё).

- **Предложение.** SHA-256 от канонического JSON (ключи отсортированы, без лишних пробелов,
  числа через `repr` float в Python) из трёх частей: имя типа расчёта, входы в базовых
  единицах, идентичность набора resolved parameters. Идентичность — SHA-256 от такого же
  канонического JSON resolved parameters, каждое значение со своим списком `NormRef` или
  `EngineerRule`.
- **С твоей стороны.** Согласиться или сказать, что ещё нужно WP3.
