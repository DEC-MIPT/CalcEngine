## 1. Пункт 9.3: где живёт код чтения

Твоя позиция (`backend-layered-architecture-split-egor-ack.md`): код загрузки и каталога
остаётся в `normatives_pipeline/`, второго загрузчика в `backend/normatives/` нет. Твой
ответ на вопрос 8 (`normatives-formula-contract-review-egor.md`): бэкенд получает функцию
и роль только на чтение. Спека WP5 запрещает бэкенду импортировать что-либо из `ml/`, куда
переезжает твой пакет, так что вызвать твою функцию на Python бэкенд не может.

- **Предложение.** Контракт между нашими зонами — база данных, а не код на Python. Ты
  владеешь небольшим набором SQL-представлений или SQL-функций только на чтение в
  `dec_normatives`: их создаёт твоя загрузка, и версионируются они вместе с ней. К ним —
  роль, которой разрешён только `SELECT` из них. Бэкенд читает только их, своим
  репозиторием (SQLAlchemy Core, параметризованные запросы), через
  `DEC_NORMATIVES_DATABASE_URL`. Загрузчик не дублируется: данные пишешь ты, я только
  читаю представления.
- **С твоей стороны.** Согласен, или предложи другой контракт, который сохраняет оба
  правила импорта (бэкенд никогда не импортирует `ml/`, `ml/` никогда не импортирует
  `backend/`).

## 2. Что возвращают представления

Что нужно бэкенду, по назначению:

- **Поиск** (`normatives-catalog`, «Full-text search»): документы, пункты и формулы,
  подходящие под запрос, с ранжированием по сходству `pg_trgm` (твой ответ 9). Каждый —
  с обозначением документа, редакцией и номером пункта или формулы.
- **Документ и его пункты** по id — для страницы каталога.
- **Resolved parameters одного типа расчёта.**
  - Для каждой формулы метода — её дерево выражения (решение 11 WP2) с единицей каждого
    символа.
  - Для каждого табличного значения и порога — значение и единица.
  - Для каждого из них — пять полей `NormRef`: `document`, `edition`, `clause`,
    `status`, `provenance`.
- **Область применения метода** (решение 15 WP2): каждая граница с величиной, видом,
  значением, включённостью и списком `NormRef`.

- **С твоей стороны.** Согласен ли с этим списком, и что из него уже есть на
  `feature/normative-parser/ml`. Я прочитал там: у `formula` пока нет колонки дерева, а
  `status` и `provenance` всё ещё константы в `build_formula_payload`.

## 3. Привязка типа расчёта к нормам

Для требования `normatives-catalog` «Binding a normative to a calculation type» нужна
запись о том, какие формулы, ячейки таблиц и границы какого документа использует тип
расчёта. Это не значение нормы, поэтому в `.yaml` оно не запрещено, но это данные
каталога.

- **Предложение.** Привязка хранится в `dec_normatives`, рядом с нормами, на которые она
  ссылается, и заполняется твоей загрузкой из небольшого реестра, которым владеешь ты.
  Бэкенд ищет параметры типа по его имени (для пилота — `foundations_shallow_r`).
- **С твоей стороны.** Согласен, или оставим привязку на стороне бэкенда: `.yaml` на тип
  с номерами формул и ячейками таблиц, но никогда не со значениями.

## 4. Выбор строки таблицы по входному значению

Пилоту нужны `M_γ`, `M_q`, `M_c` из таблицы 5.5 для `φ_II`, которое задаёт инженер. Движок
принимает один `TableValue` на символ, значит, кто-то должен выбрать строку. В таблице
`coefficient` есть `row_index` и `col_index`, но нет значения в заголовке строки.

- **Предложение.** Хранить значение заголовка каждой строки и столбца с единицей (для
  таблицы 5.5 — `φ_II` в градусах), чтобы бэкенд выбирал строку, у которой заголовок
  равен входу. Вход между двумя строками отклоняется, пока правило самой нормы для этого
  случая не записано с её пунктом. Сам бэкенд не интерполирует.
- **С твоей стороны.** Согласен, или скажи, как бы ты ключевал ячейки.
