## Решения Акима (2026-10-19)

1. **Отметка верификатора.** Это отдельная запись верификации, которая служит гейтом
   профиля `strict`. `NormRef` остаётся `unverified` / `machine-extracted` до WP3, поэтому
   `calculation-core-contract` и `normative-catalog-backend` не меняются.
2. **Формат данных.** YAML, записи повторяют строки `catalog_read`. Код сборки общий, поэтому
   оба источника выдают одни и те же объекты параметров.
3. **Где хранится запись верификации.** Рядом со значением. Изменённое значение возвращается
   в `pending` через `value_digest`.
4. **Что делает `strict`.** Отказывает на запросе: `503 parameter_source_unavailable`, имя
   параметра пишется в лог. Битый файл не даёт приложению стартовать.
5. **Срок отключения.** Задаётся датой и событием. После даты при старте выводится
   предупреждение, и тест бэкенда намеренно падает.
6. **Объём данных.** Данные R пилота входят в критерий готовности (`ex1` в `strict`). Данные
   фазы 1b — отдельная порция на третьей фиче.
7. **Исключение из решения 3 `backend-layered-architecture`.** Выбрано после пробного
   validate. Пробная MODIFIED-дельта «No hardcoding» проходит `openspec validate --strict`,
   но OpenSpec предупреждает: «Archive would refuse this delta: backend-architecture: target
   spec does not exist». Поэтому исключение — ADDED-требование, которое называет все четыре
   ограничиваемых требования:
   - «No hardcoding» и «Engineer-set parameters stored in YAML» (`backend-layered-architecture`);
   - «Calculation parameter source» (`calculation-api`);
   - «Catalog parameter source» (`normative-catalog-backend`).

   Задача 1.4 добавит MODIFIED-дельты после архивации этих change.
8. **Согласие.** Егор и PM устно согласились на временную базу 2026-10-18 (со слов Акима).
   В `design.md` это записано одной строкой, без раунда вопросов.
