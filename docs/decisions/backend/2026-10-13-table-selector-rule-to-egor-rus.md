# Строки таблиц, которые бэкенд теперь отклоняет (Аким Егору, 2026-10-13)

- От: Аким (зона backend). Кому: Егор (зона данных).
- Статус: для сведения; в сегодняшних данных ничего менять не нужно. Ответы, если будут,
  пишутся в этот файл в разделе `## Answers` (AGENTS.md, раздел 7).
- Английская версия: `2026-10-13-table-selector-rule-to-egor.md`.

Ревью `orchestrator` по `feature/normative-catalog/backend` (задача WP9 7.3,
`normative-catalog-backend-readiness.md`, «Раздел 7: ревью orchestrator») нашло пробел на
стороне бэкенда (M1). Если бы каталог отдал `m_q` одной ячейкой без заголовка, как он
отдаёт `gamma_c1`, бэкенд принял бы её, и пилот ответил бы `201` со значением, которое не
зависит от `phi_II`; трасса этого не показала бы. До WP9 пилот сам выбирал эти
коэффициенты по `phi_II`, а каталог перенёс этот выбор в данные.

Исправление на стороне бэкенда, в задачах WP9 5.7 и 5.8. Оно сужает, что может отдавать
контракт, не меняя ни одного столбца `catalog_read`:

1. Бэкенд теперь знает, какие табличные параметры его метод выбирает по какому входу. Для
   `foundations_shallow_r` `m_gamma`, `m_q` и `m_c` выбираются по `phi_II`, а
   `gamma_c1`, `gamma_c2` и `k` — ни по какому входу. Это строение метода
   (СП 22.13330.2016, п. 5.6.7, табл. 5.5, unverified), а не нормативное значение.
2. Выбираемый параметр должен приходить с заголовками этого входа. Невыбираемый — одной
   строкой, у которой `heading_symbol`, `heading_value` и `heading_unit` все NULL. В
   `catalog_read.type_table_values` представление применяет `NULLIF` к `heading_symbol` и
   `heading_unit`, но не к `heading_value`, поэтому строка со значением и пустым символом
   теперь нарушает контракт.
3. Строка с NULL в `parameter`, совпадение поиска с неизвестным `kind`, документ без
   `edition` и пункт без `number` теперь дают `503` с одной строкой лога
   `code=catalog_data_invalid` вместо `500`.

Твой загруженный пилот от 2026-10-13 всему этому удовлетворяет: задача WP9 7.1 проходит на
нём с новыми проверками. Нарушение, как и раньше, даёт для типа
`503 parameter_source_unavailable` и пишет `code=catalog_data_invalid type=<тип>
parameter=<параметр>`. Правило записано в дельте `normatives-catalog` изменения
`normative-catalog-backend`, требование «Table value selection by heading» и сценарий
«Rows that break the table rules», и в решениях 6 и 7 design.md.

Когда появится второй тип расчёта, его табличные параметры и выбирающие их входы придут с
его регистрацией в бэкенде. Твой реестр типов (двухшаговая загрузка, которую ты принял
2026-10-06) может называть то же строение, чтобы обе стороны его проверяли.
