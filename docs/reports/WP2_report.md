## Допущения

1. **`security` — четвёртая capability**, которой нет в разделе 3.2 роадмапа. Её добавление одобрено в плане.
2. **Детерминизм R1 и `result_id`.** Если `result_id` уникален для каждого запуска, два одинаковых прогона дали бы разные конверты. Поэтому `result_id` назначает сервисный слой при сохранении, и в сравнении конвертов он не участвует.
3. **«Граница» из R3** — это граница движка: входной и выходной адаптер вокруг формул, а не граница всей системы. Пересчёт и проверка применимости стоят в адаптере и остаются чистыми.
4. **Отказ — это тоже конверт** с вердиктом `refused`, а не исключение. Вердикты: `pass` / `fail` / `refused`.
5. **Подписи в отчёте** управляются одной настройкой. Значение по умолчанию выбирается после сверки с ГОСТ Р 21.101 (задача 6.5). До этого требование остаётся `unverified`.
6. **«Validated envelope» из роадмапа переименован в «validated range»**, чтобы не путать его с конвертом результата.
7. **`input_hash`** в `design.md` — это только предложение: SHA-256 от входов в базовых единицах, типа расчёта и идентичности набора параметров. Требование фиксирует лишь одно: одинаковые входы дают одинаковый хеш.
8. **Пересечения с WP1 обойдены.** Требования, которые WP1 удаляет или меняет, не тронуты, а разметка verified/unverified взята по ссылке на требование WP1 «Norm reference status». WP1 должен архивироваться первым.

## Найденные конфликты (чужие файлы не правились)

- **B5.** Задача 6.2 в `backend-layered-architecture` противоречит R1. Требование «Parameters stored in YAML» с R1 согласуется. Синхронизация с этим change заведена как задача 7.2 для WP5.
